# 需求创建、产品原型持续迭代与 GitLab 自动发布实施方案

- 更新日期：2026-11-10
- 状态：待实施；本文不是已实现能力说明。
- 需求依据：用户确认的唯一标识、取消低保真、requirements 目录、需求资料与产品原型分仓管理（2026-11-10 最新明确要求），以及产品原型持续迭代、需求分支预览、合入产品原型和验收版本绑定。
- 当前范围：仅更新方案文档，不修改代码、部署配置或服务器。

## 1. 目标与核心模型

一个产品使用独立的需求资料仓库与产品原型仓库，分别保存需求资料和一套持续演进的高保真 HTML 原型，通过需求 ID、仓库标识及精确版本引用关联。工具仓库 `Requirement-AI-Toolkit` 维护技能、模板、校验和发布能力。

需求负责记录变化，产品原型累积变化，发布快照保存历史。取消“每个需求独立维护一套原型源码和正式原型包”的设计，需求资料与产品原型必须分仓，不要求两个仓库同步提交或同时发布。

| 对象 | 职责 |
| --- | --- |
| 需求资料 | 原始输入、确认、修改范围、文档、评审和验收记录 |
| 产品原型源码 | 当前产品的页面、流程、交互和模拟数据 |
| 需求分支 | 隔离未合入的修改，修改同一套产品原型源码 |
| 需求预览 | 展示分支效果，不更新产品最新入口 |
| 产品发布版本 | 主分支成功发布的不可变完整快照 |
| 验收记录 | 将需求绑定到实际查看并确认的产品发布版本 |

目标服务器为私网 `10.94.164.176`。第一版采用 GitLab CI/CD、内网 Runner 和一个 Nginx 静态服务；不开发自建 Webhook 服务，不为每个原型启动应用或容器，不包含外网入口或统一登录。

## 2. 创建需求与唯一标识

创建需求第一步提供标识输入，留空时自动生成。

| 项目 | 规则 |
| --- | --- |
| 手动输入 | 仅英文字母和数字，至少包含一个字母和一个数字 |
| 统一格式 | 去除首尾空白，统一转为小写 |
| 自动生成 | req＋日期＋随机字母数字，例如 `req20261110a7f3c9` |
| 唯一范围 | 同一产品的需求资料登记，包括已归档需求 |
| 手动重复 | 提示重新输入，不擅自修改 |
| 自动重复 | 重新生成并校验，直到唯一 |
| 标识生命周期 | 名称修改、归档和下线均不改变或释放标识 |

先校验格式，再检查登记及现有目录，包括旧目录映射，通过后创建 `requirements/<需求标识>/` 并登记。同机创建防止检查与创建之间的并发冲突。

不同分支并行创建时，合入检查再次校验唯一性，发布前仍保留最终检查；重复标识不得覆盖已有需求。合入前阻断需要配置相应的分支合并检查。

跨产品用“项目标识＋需求标识”定位。原型需求分支名称等于规范化后的需求 ID，例如 `req002`，登记同时保存原型仓库和分支。同一需求后续修订新增记录，同名分支重用规则实施前确定，不覆盖历史验收。

## 3. 仓库与目录结构

```text
业务需求仓库/
├─ README.md
├─ .gitlab-ci.yml
├─ requirements/
│  └─ <需求标识>/
│     ├─ index.html
│     ├─ docs/
│     │  ├─ prd.html
│     │  ├─ flowchart.html
│     │  └─ acceptance.html
│     ├─ assets/                 # 需求文档专用资源
│     ├─ working/
│     │  ├─ discovery/
│     │  ├─ specs/
│     │  └─ reviews/
│     ├─ sources/
│     └─ acceptance-records.json # 正式验收及后续修订记录
├─ publish/
│  └─ projects.json           # 需求、原型仓库与分支关联
└─ .gitlab-ci.yml

产品原型仓库/
├─ prototype/
│  ├─ index.html
│  ├─ flows/
│  │  └─ <flowId>.html
│  └─ assets/
│     ├─ styles/
│     ├─ scripts/
│     ├─ images/
│     └─ data/                   # 需要时保存模拟数据
├─ design-system/
└─ publish/
   └─ projects.json
```

`requirements/` 替代 `outputs/product-requirements/`。需求目录保存需求资料，不再包含独立维护的 `prototypes/` 或产品设计系统。产品原型统一位于独立原型仓库的 `prototype/`，设计系统位于该原型仓库根目录；不设置低保真目录。

`working/discovery/` 保存原始需求、明确确认和业务模型；`working/specs/` 记录本需求涉及的 flowId、screenId、修改规格及约束；`working/reviews/` 保存评审与验证记录。这些是持久资料，纳入 Git，不因不发布而清理。仅创建当前阶段所需文件。

| 存储层 | 生命周期 |
| --- | --- |
| 需求资料、产品原型源码、设计系统 | 在 Git 中持续维护 |
| CI 打包目录和压缩包 | 临时生成，不回写源码目录、不提交 Git |
| 服务器或制品存储中的发布快照 | 不可变，按引用和保留策略维护 |

历史快照不复制进每个需求目录。需求记录保存版本关联；日常发布状态由部署端维护。

## 4. 需求实施与产品合入流程

```text
输入或生成需求标识
        ↓
解析当前原型最新正式基线，在原型仓库创建以需求 ID 命名的分支
        ↓
需求澄清与业务模型确认
        ↓
PRD、流程图及验收场景确认
        ↓
复用视觉方向与设计系统
        ↓
检查现有产品原型，在需求分支修改
        ↓
发布需求预览，交互与视觉评审
        ↓
用户确认可以合入产品原型
        ↓
同步主分支、解决冲突、复查受影响页面
        ↓
通过 Git 合并进入产品主分支
        ↓
自动发布产品最新原型
        ↓
核对合入后实际版本，用户确认验收
        ↓
保存需求验收绑定
```

取消低保真生成、评审及其前置条件。需求文档不再等待低保真确认；高保真评审发现的业务问题回补文档。已有确认沿用，不重复增加审批。

实施前检查已有能力，保留满足要求的页面与交互。已有流程沿用稳定 flowId、screenId，新增业务流程才增加页面；不能每次需求都重新生成整套产品原型。首次没有原型时建立初始产品原型。

“合入产品原型”通过 Git 合并完成，不手工复制需求目录里的 HTML。需求评审通过代表可以合入；验收完成代表合入后的实际效果已确认。合并或发布失败不得标记交付完成。

若其他需求已更新主分支，必须基于合并结果重新检查受影响场景；不能只凭旧分支预览通过就跳过合入后的验证。

## 5. 分支与发布环境

原型需求分支名称等于需求 ID，例如 `req002`，不加额外前缀。产品主分支以实际配置为准，例如 `main`。需求资料仓库的编辑分支沿用其仓库约定，不要求机械创建第二个同名分支。

| 操作或分支 | 行为 |
| --- | --- |
| 本地保存、git commit | 不触发远端发布 |
| 推送原型仓库已登记需求分支 | 更新原型预览，关联指定的需求文档修订 |
| 推送需求资料仓库分支 | 按该仓库规则更新文档预览，不重发原型 |
| 推送未登记分支 | 可执行检查，不自动部署 |
| 合入原型主分支 | 发布变化的统一产品原型 |
| 合入需求资料主分支 | 发布变化的需求文档及导航 |
| 明确保存中途评审快照 | 固定引用当次预览版本，非必填步骤 |
| 确认验收 | 绑定用户实际确认的主分支成功发布版本 |
| 重试失败任务 | 根据目标环境成功状态补发 |

需求分支预览是完整产品原型在该分支下的效果，不是只包含本次修改的零散页面。不同需求分支使用不同预览命名空间；不得更新产品最新入口。

合入后的产品版本可能包含其他已完成需求，这符合持续迭代模型。分支预览版本不能直接冒充合入后产品验收版本。

原先“只使用一个 preview 发布分支”的设计由上述分支模型替代。实际推送、合并与服务器变更按用户授权执行，方案本身不构成执行授权。

## 6. 发布单位、清单与增量规则

发布单位调整为：按需求独立的文档包、按产品统一的原型包，以及按需更新的导航。分支预览复用同样的打包方式，但部署到独立环境。

需求资料仓库的 `publish/projects.json` 保存项目标识、需求登记、资料路径、原型仓库与分支关联及文档发布配置。原型仓库独立维护原型包发布配置和依赖。跨仓引用保存仓库标识与精确提交，不能只存分支名。正式验收绑定以需求目录的验收记录为准，避免维护多个相互冲突的绑定来源。

对最终发布文件计算指纹：

```text
包指纹 = SHA-256（排序后的相对路径 + 各文件内容摘要）
```

比较基准是该包在目标环境中当前成功发布的内容，而不是上一条 Git 提交。分支预览和产品正式环境分别记录状态；首次进入某环境时，即使其他环境已有同内容，也须建立该环境的有效入口和记录。

| 变化 | 发布行为 |
| --- | --- |
| 只修改需求 A 文档 | 仅更新 A 文档，不重新发布产品原型 |
| 修改产品原型 | 在对应分支环境发布产品原型包 |
| 新建需求但未改原型 | 发布有效文档或导航，不制造新的产品原型内容版本 |
| 共享设计系统资源变化 | 重新计算实际依赖它的包，内容变化才部署 |
| 只修改过程记录 | 不更新页面包，除非显式发布内容确有变化 |
| 保存验收记录 | 更新需求导航或文档关联，不产生新原型内容版本 |
| 内容一致 | 跳过重复上传和版本切换 |
| 上次失败 | 与最后成功状态比较，继续补发 |

产品原型第一版完整打包，不按需求拆包。原型有变化时发布完整新快照，需求文档仍按需求增量发布。后续只有明确存在独立运行模块时才考虑按模块拆包。

发布包包含必要 HTML、CSS、JavaScript、图片及模拟数据，不引用会被覆盖的共享运行资源。打包检查相对路径和缺失依赖，动态依赖须显式登记。版本复现不应依赖会变化的真实业务接口。

指纹排除打包时间和流水线编号等部署元数据；生成器避免每次写入变化的时间而触发无意义发布。每次相关分支推送执行轻量状态检查，路径过滤不能漏掉失败补发。

## 7. 自动部署、并发与失败恢复

```text
检查登记、唯一标识和产物
    ↓
收集依赖、打包、计算指纹
    ↓
取得目标环境部署锁，重新读取成功状态
    ↓
只上传变化包到临时目录并校验
    ↓
建立不可变版本目录并检查入口与资源
    ↓
原子切换该环境的入口
    ↓
HTTP 检查、记录成功状态与访问链接
```

同一目标环境的部署串行执行，切换前检查任务顺序，防止旧任务覆盖新版本。预览与正式环境的目录和部署状态隔离，分支不得通过自定义路径覆盖正式目录。

上传或校验失败保留旧入口；切换后验证失败恢复上一入口。文档和原型部分成功时分别报告，重试只补发未完成内容。失败发布不能成为验收绑定目标。

目录或登记删除仅报告待下线，不自动清空线上内容。导航只链接有效发布对象。临时文件和内部状态不对外开放。

HTTP 检查不能替代浏览器业务交互和视觉验收。部署端状态至少记录环境、包类型、提交 SHA、指纹、流水线、发布时间、当前及上一成功版本。

## 8. 三层版本机制与访问入口

| 层次 | 保存内容 | 用户操作 |
| --- | --- | --- |
| Git 提交 | 源码和需求资料历史 | 正常提交，无须手工命名版本 |
| 发布版本 | 成功发布的完整不可变快照 | 系统自动生成标识和链接 |
| 验收绑定 | 需求引用的正式发布版本 | 确认实际查看版本验收通过 |

版本标识由工具生成，可包含流水线编号及提交摘要，例如 `p-184-a7f3c9`。内容不变时可复用已有快照，但需记录当前提交或合入事件与该快照的对应关系，保证后续验收可以追溯。

拟定访问路径如下，尚未配置：

| 用途 | 路径 |
| --- | --- |
| 产品最新原型 | `/products/<项目>/prototype/` |
| 产品固定原型版本 | `/products/<项目>/prototype/versions/<版本>/` |
| 需求分支预览 | `/products/<项目>/previews/<分支键>/prototype/` |
| 预览固定版本 | `/products/<项目>/previews/<分支键>/prototype/versions/<版本>/` |
| 需求分支文档预览 | `/products/<项目>/previews/<分支键>/requirements/<需求>/docs/` |
| 正式需求入口 | `/products/<项目>/requirements/<需求>/` |
| 正式需求文档 | `/products/<项目>/requirements/<需求>/docs/` |
| 文档固定版本 | `/products/<项目>/requirements/<需求>/docs/versions/<版本>/` |

分支键由工具生成，避免分支名称字符和重名导致路径冲突。固定入口引导到具体版本路径，避免页面加载跨版本资源。最新入口不使用长缓存，版本资源可使用较长缓存。

正式需求页主要展示“查看需求文档”“查看验收原型”“查看产品最新原型”。未验收时明确显示待验收，并提供已登记的预览入口，不用最新版伪装验收结果。普通技术版本默认不要求用户管理。

## 9. 验收绑定与文档引用

默认每个需求修订只绑定一个正式验收快照。基线、评审版本不作为用户必填管理项；基线提交由工具记录，中途评审快照仅在用户要求留存时保存。

验收操作要求：

1. 确认需求已合入，且目标产品版本发布成功。
2. 获取用户实际打开并确认的版本标识，不在操作时重新抓取可能已变化的“最新版”。
3. 核对该版本与合入结果的关联；无法确定用户确认的是哪个版本时先核实，不能猜测。
4. 将验收记录写入需求资料并按授权提交，保存需求标识、修订、需求资料仓库及文档提交、原型仓库及源码提交、原型版本和固定链接、产物摘要、合入关联、实际确认依据及时间；场景与标注存在时一并固定其修订。
5. 更新需求导航。绑定已有快照，不复制一套原型源码，也不重新生成原型版本。

如果从查看到确认期间产品已更新，仍绑定用户实际确认的那个合入后版本。若用户实际查看的仅是旧分支预览，应先核对合入后的正式版本，不能直接标记最终验收。

```text
需求 A 合入并验收 → 绑定产品版本 184
需求 B 合入并发布 → 产品版本 185
需求 C 合入并发布 → 产品版本 186

产品最新入口 → 186
需求 A 验收入口 → 184
```

需求验收后再修改，新增修订及验收记录，保留原记录。验收记录和所绑定的需求文档版本建立关联，避免后续文档修改改变历史验收依据。记录元数据由工具管理，不要求用户填写技术版本表。

已发布文档引用明确的原型版本及页面锚点；产品最新链接单独标明用途。需求尚无原型或验收版本时明确标注状态。若文档引用尚未成功发布的目标版本，阻止该关联发布。引用变化触发文档或导航更新，不改变已有不可变文档版本。

## 10. 回滚、保留和分支清理

回滚产品最新入口只改变展示，不修改 Git 历史，也不改变需求验收绑定。若要后续开发继续基于旧行为，需要在源码中撤销相关变更并提交，避免下次部署恢复被回滚内容。

需求文档可按需求回滚；产品原型回滚作用于统一产品入口，不能承诺只撤销某个需求而不影响其他需求。只撤销某需求的行为应通过源码变更和新产品版本实现，并验证相互依赖。

必须保留当前版本、正式验收引用版本、明确留档的评审版本，以及被保留文档引用的原型版本。包资源随版本保存。其他普通发布版本的数量和期限实施时确定，未确认前不自动清理。

需求分支合入后可以清理可变预览入口，但不能删除仍被明确留存的评审记录引用的快照。归档需求不释放标识。历史记录只保存 Git 提交而没有可用快照，不算满足历史原型可访问的要求。

## 11. 发布范围和环境条件

文档包默认包含该需求的正式文档、必要资源及允许发布的导航信息。产品原型包包含产品原型及实际依赖的设计系统资源。工作记录、可编辑源文件默认不公开，需要时显式配置。

CI 临时产物不提交 Git；日常部署不反向写源码仓库。用户确认触发的验收记录写入是单独的需求资料更新，若触发流水线只更新变化文档或导航，不重新发布未变的原型。

实施前核实 GitLab 地址和版本、需求资料仓库与原型仓库、各自主分支、分支保护及合并检查、Runner 执行环境、服务器系统、Nginx 状态、端口与路径冲突、空间和网络连通性。Runner 须能访问 GitLab 和部署服务器，访问者须能连通该私网。

部署使用专用账号和 SSH 密钥，核验主机密钥；凭据不写入仓库、方案、产物或日志。未授权的分支任务不能获得正式部署权限。GitLab 仓库权限不等同于页面访问权限。

## 12. 旧产物兼容与迁移边界

新需求使用 `requirements/`，新原型修改统一落在独立原型仓库的 `prototype/`。已有 `outputs/product-requirements/` 或需求内原型不自动删除、批量搬迁或机械合并。

实施时先盘点旧产物，由用户明确哪一套作为当前产品原型基线。其他旧原型按实际来源保留为历史资料或导入固定快照；不能凭目录时间推断它已验收，也不能将多套不同需求原型直接覆盖到一起。

旧需求通过登记映射兼容，分配标识时检查冲突。已有低保真只作历史资料，新流程不生成也不要求补齐。明确迁移时更新登记、内部链接和校验，验证依赖完整。

本文的新产品级路径替代之前尚未实施的按需求原型路径设计；若环境核实时发现已有对外地址，先制定兼容映射，不擅自使历史链接失效。不借目录迁移修改业务规则。

## 14. 验收标准

| 场景 | 预期结果 |
| --- | --- |
| 输入或自动生成需求标识 | 合法且在仓库内唯一，归档标识不复用 |
| 分支并行创建重复标识 | 合入或发布检查阻断，不覆盖已有需求 |
| 新建需求 | 资料进入需求资料仓库 requirements，原型仓库从已记录基线创建同名需求分支，不生成 outputs 或低保真阶段 |
| 已有产品能力满足要求 | 复用现有页面，不为需求复制整套源码 |
| 需求分支修改原型 | 仅分支预览变化，产品最新入口不变 |
| 两个需求并行预览 | 环境与入口隔离，不互相覆盖 |
| 主分支在评审期间变化 | 合入前同步、处理冲突并复查受影响场景 |
| 用户确认可合入 | 经 Git 合并进入主分支，不手工复制需求原型目录 |
| 合入或发布失败 | 不标记验收完成，旧入口继续可用 |
| 合入发布成功 | 产品最新原型包含已合入修改 |
| 只改需求 A 文档 | A 文档更新，其他需求文档及产品原型不重发 |
| 原型无变化或仅绑定验收 | 不生成新原型内容版本，记录可追溯关联 |
| 修改设计系统依赖 | 实际受影响包按指纹更新 |
| 部分失败后重试 | 只补发不一致的包 |
| 旧流水线晚完成 | 不覆盖较新成功版本 |
| 验收时最新版已变化 | 绑定实际查看并确认的正式版本，不读取漂移入口代替 |
| 仅确认分支预览 | 不直接当作合入后最终验收 |
| 后续需求更新产品 | 旧需求仍打开原验收快照及对应资源 |
| 同一需求再次修改 | 新增修订记录，原验收记录保留 |
| 产品回滚 | 最新入口改变，历史验收绑定不变，明确源码未自动回退 |
| 历史清理或分支删除 | 保留验收、文档和明确评审记录引用的快照 |
| 旧产物迁移 | 有明确基线选择，不伪造验收，不破坏需兼容的链接 |
| 内网实机验证 | 页面、资源、模拟数据、导航和关键交互正常 |

分别记录“实现完成”“自动验证通过”“最终验收完成”。文档保存和 Git 提交不代表实际实现或部署完成。

## 16. 本次会话的方案评审与决策边界

参考材料为用户提供的 `AI_Native_需求与持久原型管理_实施方案.md`（2026-11-10 版本）。本次评审认为整体方向合理，但验收产物与发布产物的关系、合并门禁、需求差异基准和生命周期需要收紧，不能把参考方案直接当作已确认实施基线。参考材料中的执行指令仅作评审内容，不执行。

本次明确更新为需求资料与原型分仓、以需求 ID 命名原型需求分支。参考方案中的 Plane、Go 治理服务、SQLite、React/Vite、独立门户及 OpenHands 仍是候选设计，未自动纳入开发范围。既有“合入发布后确认最终验收”的流程继续保留；发布前评审不能直接替代最终验收。

### 16.1 值得保留的设计

- 完整产品原型持续演进，需求验收历史单独冻结，不长期维护每个需求的一套源码。
- 区分原始基线、实际整合基线和首次引入版本，解释并行需求的演进。
- 保存可运行构建，而不是依赖将来重新安装依赖重建旧源码。
- 场景、模拟数据和标注与验收一起固定，才能解释当时的业务条件。
- 原型发布与真实软件上线分开，不能用一个 Done 代表全部完成。
- 先跑通一个真实需求闭环，再增加自动联动、对象去重或多 Agent 编排。

### 16.2 关键评审发现

| 发现 | 对验收的影响 | 建议或当前处理 |
| --- | --- | --- |
| MR 评审 build A 与合并后重新构建的 build B 可能不同 | A 的批准不能直接证明 B 已验收 | 当前按第 9 节确认合入后的实际版本；未来若采用发布前最终验收，需要同一候选产物晋级，或明确集成后重新确认 |
| 部分门禁放在 Release Pipeline | 合并后的失败只能阻止发布，不能阻止合并 | 合并前验证源 HEAD、目标基线、允许合入的评审依据及集成结果；主线变化后重新验证 |
| origin_baseline 直接作为需求差异起点 | 会混入其他并行需求的改动 | 分开表示背景变化和本需求实际集成前后变化 |
| 未验收、多次验收、多 MR 状态不完整 | 默认页面与需求完成条件无法确定 | 明确待验收状态，保留历史记录；第一版建议每个修订一个主要原型 MR |
| 用内容 digest 标识 build，却只保存一个 pipeline 和 commit | 相同产物的多个构建来源可能丢失 | 分开记录构建执行与内容产物；复用产物不丢失来源 |
| version、MR IID 缺少项目限定 | 多产品或多仓库标识可能冲突 | 版本带产品标识，MR 带 GitLab 项目标识，SHA 带仓库标识 |
| 多部署路径下重新设置构建 base | 产物变化或静态资源、深层路由失效 | 固定产物地址，入口解析或跳转；验证刷新、懒加载与场景初始化 |
| 基础权限与审计全部推迟到后期 | 无法支撑早期可信验收和受限访问 | 相应功能上线时具备必要身份、授权和审计；企业级 SSO、复杂门户可后置 |

GitLab Free 的 MR approval 是可选批准，不会直接阻止未批准合并；原生 merged results pipelines 属于 Premium/Ultimate。实际部署需要核验许可证并落实合并前检查或受控替代流程。只把校验脚本放入可由普通 MR 修改的仓库，不能证明门禁不可绕过。初期人工受控合并应称为流程门禁，不宣称已实现技术强制门禁。

跨仓 PRD 发生变化时，应依据具体修订判断是否需要重新评审，不能只读取当前文档。验收记录提交本身不得循环改写被验收文档的历史引用。需求的必需变更集合、变更后的失效规则和验收记录默认选择规则须在实施时明确。

- [GitLab MR approvals](https://docs.gitlab.com/user/project/merge_requests/approvals/)

## 17. 需求 ID 分支模型的具体约定

### 17.1 创建、来源与跨仓失败

“最新版本”建议明确为最新成功发布的正式原型基线，而非未经发布验证的任意 main HEAD。创建时解析出具体版本与提交，再创建同名分支；不得用之后变化的主线重写原始来源。若主线领先正式基线，合入前仍须验证最新目标主线。首次没有原型时先建立初始基线。

跨仓创建不是原子事务。需求已登记但原型分支创建失败时，显示“原型分支待创建”并允许幂等重试。同名分支已存在时核对归属，不擅自重置或接管。需求资料仓库与原型仓库分别报告发布成功或失败，目标尚未成功发布时不得登记有效链接。

会话中的 `REQ-001`、`REQ-002` 是解释用名称；实际创建继续遵循第 2 节既有规范，例如 `req001`、`req002`，并以该 ID 原样命名分支。

### 17.2 三层关联

| 关联 | 回答的问题 | 是否变化 |
| --- | --- | --- |
| 需求 ID → 原型仓库及同名分支 | 这个需求正在什么地方修改？ | 分支 HEAD 持续变化 |
| 需求 ID → 具体评审或验收提交、构建 | 当时确认了什么？ | 每条记录固定 |
| 需求 ID → 正式发布版本 | 何时进入完整产品原型？ | 首次引入记录固定 |

建议由工具自动保存以下关联，避免产品经理维护技术版本表：

```yaml
requirement_id: req002
prototype_repository: pos-prototype
prototype_branch: req002
origin_baseline:
  version: v0.0.1
  commit_sha: <创建时基线提交>
working_base_sha: <已实际整合的基线提交>
accepted_snapshot:
  docs_repository: product-docs
  docs_commit_sha: <实际确认的文档提交>
  prototype_commit_sha: <实际确认的正式原型提交>
  build_id: <实际确认的产物摘要>
introduced_in:
  version: v0.0.2
  commit_sha: <首次完整引入的正式提交>
```

分支不是历史版本。分支继续提交或吸收主线后内容会变化，历史入口必须指向固定产物。分支合并后可以保留或删除，但历史追溯不能依赖分支仍然存在。

### 17.3 并行需求的双向合并

1. `req001`、`req002` 均从 v0.0.1 创建。
2. `req002` 先完成并合入 main，发布 v0.0.2。
3. `req001` 将最新 main 合入自己的分支，处理冲突并验证相关场景；必要时重新评审。
4. `req001` 合入 main，发布 v0.0.3。
5. `req002` 的历史验收保持实际确认的旧版本，当前产品入口指向 v0.0.3。

`main → req001` 是在途需求吸收最新原型，`req001 → main` 是将需求纳入完整原型。Git 无文本冲突不代表无业务冲突；不同文件也可能共同影响结算金额等行为。已完成需求不需要持续同步主线。

`req001` 的需求差异不能默认比较 v0.0.1 与 v0.0.3，因为会混入 `req002`。记录实际集成前后的基线，并用人工语义清单解释本需求变化；多 MR 时保留变更集合及完成确认。

### 17.4 查看与清理

| 阶段或模式 | 内容 |
| --- | --- |
| 开发中 | 同名需求分支最新有效预览，注明尚未验收 |
| 待评审 | 本轮具体提交的固定预览 |
| 历史验收 | 实际验收的正式产物、需求文档和场景 |
| 当前产品 | 最新成功发布的完整原型 |

同一需求再次修订新增验收记录，不覆盖旧记录。没有验收时显示待验收；新一轮驳回不改写过去通过记录。若后续引入语义标注，当前目标不存在时提示失效，不自动匹配近似元素。

## 18. 本次讨论后的实施顺序补充

第 13 节工作按以下最小闭环组织，避免先建大平台再验证核心关联：

1. 核实两个仓库、原型初始基线和实际发布环境。
2. 跑通一个需求 ID、一份 PRD、一个同名原型分支、一个业务场景、一个 MR 预览、一次合入与正式验收绑定。
3. 用第二个并行需求验证基线变化、双向合并、回归和旧验收不变。
4. 完善增量发布、跨仓部分失败补发、回滚和引用保留。
5. 有需要后增加旧版本按需恢复、自动联动、标注门户及语义差异。

第一版可以让所需历史快照全部在线，Plane 链接手工维护（如采用 Plane），差异先用人工清单。后续归档恢复须校验摘要、对同一产物加恢复锁、安全解压并原子进入缓存；损坏归档应报告，不能从最新源码静默重建替代。热缓存清理不能删除唯一历史副本。

分仓不意味着自动迁移既有资料。旧同仓数据须先盘点、确认基线并制定链接兼容，再进行授权迁移。本轮不移动资料、不创建业务分支、不修改代码或部署。

与最新明确要求对应的检查：资料与原型分仓；原型需求分支名称等于需求 ID；原型改动在该分支完成并通过合并同步。其他评审建议包括跨仓创建失败重试、精确来源追溯、需求差异和归档恢复等；保存这些建议不代表用户已逐项采纳为新增开发要求，实施时仍按原始需求及后续明确确认确定范围。
