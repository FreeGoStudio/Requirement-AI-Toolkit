# 需求创建、HTML 产物组织与 GitLab 自动发布实施方案

- 更新日期：2026-11-10
- 状态：方案已整理，尚未实施
- 需求依据：本次讨论中用户确认的取消低保真、唯一标识、以 `requirements/` 承载完整需求资料，以及文档与原型独立发布要求。
- 当前授权范围：保存方案文档；不修改代码、部署配置或服务器。

## 1. 目标与边界

采用需求与原型同仓管理、按需求分目录、GitLab CI/CD 自动发布、文档与原型独立增量发布和版本管理的方式。目标服务器为私网 `10.94.164.176`。

```text
确定需求唯一标识
        ↓
需求澄清与业务模型确认
        ↓
PRD、流程图与验收场景
        ↓
视觉方向与设计系统确认
        ↓
高保真 HTML 原型
        ↓
交互与视觉验收
        ↓
提交并推送 GitLab 发布分支
        ↓
文档与原型分别检查、增量发布
        ↓
返回内网访问链接
```

取消低保真生成、低保真评审及其前置条件。需求文档不再等待低保真确认后生成；高保真评审发现的业务问题回补需求文档。

页面可以在评审过程中发布，不必等待最终验收。发布成功、自动检查通过、用户最终验收是三个独立状态。

第一版面向内网，不引入自建 Webhook 服务、业务后端、每个原型独立容器、外网入口或统一登录。

## 2. 创建需求与唯一标识

创建需求第一步提供标识输入，留空时自动生成。

| 项目 | 规则 |
| --- | --- |
| 手动输入 | 仅英文字母和数字，至少包含一个字母和一个数字 |
| 格式统一 | 去除首尾空白，统一转为小写 |
| 自动生成 | `req`＋日期＋随机字母数字，例如 `req20261110a7f3c9` |
| 唯一范围 | 同一业务需求仓库，包括已归档需求 |
| 手动标识重复 | 提示重新输入，不擅自改名 |
| 自动标识重复 | 重新生成并检查，直到唯一 |
| 标识用途 | 需求目录、发布登记、部署状态和访问地址 |
| 修改需求名称 | 不改变标识 |
| 归档或下线 | 保留标识登记，不重新分配 |

创建时先校验格式，再检查登记和现有需求目录，通过后创建 `requirements/<需求标识>/` 并登记。同机创建须防止检查与创建之间的并发冲突。检查范围包含登记中映射的旧目录，避免新旧结构使用同一标识。

不同分支并行创建时，本地检查不能保证全仓实时唯一。合入时再次校验，重复标识不得覆盖已有需求或触发部署。合入前阻断需要目标分支配置相应合并检查；发布流水线仍保留最终检查。

不同业务仓库通过项目标识隔离，完整定位键为“项目标识＋需求标识”。

## 3. 仓库划分

需求文档和原型放在同一业务需求仓库，工具与业务内容分开。

| 仓库 | 内容 |
| --- | --- |
| `Requirement-AI-Toolkit` | 技能、生成模板、校验脚本、通用发布能力 |
| 业务需求仓库 | 原始需求、澄清与确认记录、正式文档、原型、资源、唯一标识登记和发布配置 |

同一业务项目可以包含多个需求，无须为每个需求创建仓库。

## 4. 目录结构

业务需求仓库以 `requirements/` 为标准根目录，去掉 `outputs/product-requirements/` 两层。`requirements/<需求标识>/` 是一个需求的完整工作目录，承载原始输入、确认过程、正式文档与原型，不是可随意删除的生成缓存，也不再另建一套平行的需求目录。

```text
业务需求仓库/
├─ README.md
├─ .gitlab-ci.yml
├─ publish/
│  └─ projects.json
└─ requirements/
   └─ <需求标识>/
      ├─ index.html
      ├─ docs/
      │  ├─ prd.html
      │  ├─ flowchart.html
      │  └─ acceptance.html
      ├─ prototypes/
      │  ├─ index.html
      │  └─ <flowId>.html
      ├─ assets/
      │  ├─ styles/
      │  ├─ scripts/
      │  └─ images/
      ├─ design-system/
      ├─ working/
      │  ├─ discovery/
      │  ├─ specs/
      │  └─ reviews/
      └─ sources/
```

不再设置 `prototypes/low/` 和 `prototypes/high/`，所有新原型均为高保真 HTML。

| 内容 | 职责 | 默认发布方式 |
| --- | --- | --- |
| 根 `index.html` | 需求导航及阶段状态 | 独立按需更新 |
| `docs/` | PRD、流程图、验收场景 | 文档包 |
| `prototypes/` | 高保真交互原型 | 原型包 |
| `assets/` | 文档和原型使用的资源 | 随依赖它的包复制 |
| `design-system/` | 设计规范及实现资源 | 必要资源随包复制，展示页按清单选择 |
| `working/` | 原始需求、澄清与确认记录、规格和评审材料 | 不默认发布 |
| `sources/` | Mermaid、BDD 等可编辑源文件 | 不默认发布，可配置下载 |

仅创建当前阶段需要的文件，不预先生成空白正式产物。

`working/discovery/` 保存原始需求、后续明确确认及业务模型，`working/specs/` 保存生成规格，`working/reviews/` 保存评审与验证记录。这些材料需要随需求纳入版本管理，不能因不对外发布而作为临时文件清理。

需求目录、发布包和服务器版本目录分别承担不同职责：

| 层次 | 内容与生命周期 |
| --- | --- |
| 仓库中的 `requirements/<需求标识>/` | 长期维护的需求资料，纳入 Git |
| CI 临时工作目录 | 打包副本、压缩包和临时校验文件，可重新生成，不提交 Git |
| 服务器发布目录 | 已发布的文档和原型版本，按版本保留策略维护 |

CI 临时产物不回写需求目录。标准仓库结构不再保留 `outputs/` 层；旧路径仅用于兼容已有资料。此次目录调整不改变需求标识、独立发布规则或对外访问地址。

## 5. 生成与评审步骤

| 步骤 | 主要工作 | 进入下一步的条件 |
| --- | --- | --- |
| 确定标识 | 输入或生成、校验、登记 | 标识合法且未冲突 |
| 需求澄清 | 保存原始需求，梳理范围和业务模型 | 关键业务规则及范围确认 |
| 需求文档 | 生成 PRD、流程图、验收场景与源文件 | 文档内容确认 |
| 视觉准备 | 复用参考和已有设计系统，必要时比较视觉方向 | 视觉方向及所需设计资产确认 |
| 高保真原型 | 按稳定 `flowId`、`screenId` 生成 HTML | 结构和资源检查通过 |
| 评审与修正 | 浏览器交互、视觉及业务场景检查 | 用户验收，或明确记录待验收项 |

已有确认继续沿用，不重复增加审批。取消低保真不代表取消业务澄清、参考分析或实际浏览器验证。

## 6. 发布单位与清单

每个需求包含三个独立更新对象：导航入口、文档包、原型包。文档包和原型包各自拥有指纹、版本及发布状态。

发布清单 `publish/projects.json` 记录：

- 需求标识、名称、状态及源目录；新需求源目录为 `requirements/<需求标识>/`，旧需求可显式映射原路径。
- 文档包和原型包各自的入口、文件清单及共享依赖。
- 导航入口。
- 文档引用的原型版本。

归档需求继续保留登记。部署端维护发布状态与历史记录，不要求流水线反向提交业务仓库。

资源依赖须明确收集。打包时保留或正确转换相对路径，检查缺失资源和越界路径；无法静态识别的动态资源显式登记。

每个包携带自己的依赖资源。历史版本不引用会被后续覆盖的公共资源，确保可以复现。清单不得包含凭据、仓库内部配置或未授权发布的过程材料。

## 7. GitLab 自动触发

采用 GitLab CI/CD，不开发独立 Webhook 接收服务。第一版建议使用 `preview` 发布分支，实际名称可配置。

| 操作 | 行为 |
| --- | --- |
| 本地保存或生成 | 不发布 |
| 本地 `git commit` | 不发布 |
| 推送普通分支 | 可检查，不部署 |
| 推送发布分支 | 自动比较并发布变化内容 |
| 重试失败任务 | 根据线上成功状态补发 |
| 明确执行回滚任务 | 切换指定包的版本 |

每次发布分支推送执行轻量状态检查。路径过滤仅作为优化，不能遗漏上次失败但尚未成功发布的包。

优先复用内网 Runner，要求同时能够访问 GitLab 和目标服务器。方案中的自动发布不替代实际操作时的远程推送授权。

## 8. 增量发布规则

文档包与原型包分别根据最终发布文件计算指纹：

```text
包指纹 = SHA-256（排序后的相对路径 + 文件内容摘要）
```

比较基准是各包当前线上成功版本，而非仅比较相邻 Git 提交。

| 变化 | 发布行为 |
| --- | --- |
| 只改文档 | 只发布文档包 |
| 只改原型 | 只发布原型包 |
| 两者都改 | 分别发布 |
| 共享资源变化 | 发布实际受影响且指纹变化的包 |
| 导航变化 | 只更新导航 |
| 过程材料变化 | 不部署 |
| 包内容不变 | 跳过上传和版本切换 |
| 新增需求 | 发布已有有效入口的包 |
| 上次部署失败 | 与最后成功状态比较，按需补发 |

指纹不包含流水线编号、打包时间等部署元数据。生成器避免仅因重复执行而改变页面生成时间。

增量以包为单位：变化包完整上传，其他包不动，避免残留已删除文件或遗漏依赖。第一版可以扫描全部登记包计算指纹；扫描不等于全量上传。

## 9. 发布流程与并发

```text
校验与打包
    ↓
在部署锁内读取线上状态并比较
    ↓
上传临时目录、校验摘要
    ↓
建立不可变版本目录
    ↓
验证入口和资源
    ↓
原子切换当前入口
    ↓
HTTP 检查与成功状态记录
```

第一版同一业务仓库部署串行执行，切换前检查流水线顺序，防止旧任务覆盖较新发布。临时上传目录和内部状态记录不对外开放。

- 上传或校验失败：保留旧版。
- 切换后检查失败：恢复该包上一入口。
- 一个包成功、另一个失败：分别报告，重试时只补发未完成内容。
- 目录或登记被删除：标记待下线，不自动删除线上文件。
- 导航只链接已成功发布的入口，避免新增需求出现无效链接。

HTTP 返回正常不等于业务交互通过，浏览器验收单独记录。

## 10. 访问地址与版本管理

一个 Nginx 托管全部静态产物，不为各原型启动独立应用。

| 用途 | 建议路径 |
| --- | --- |
| 需求入口 | `/prototypes/<项目>/<需求>/` |
| 最新文档 | `/prototypes/<项目>/<需求>/docs/` |
| 最新原型 | `/prototypes/<项目>/<需求>/prototypes/` |
| 文档历史版本 | `/prototypes/<项目>/<需求>/docs/versions/<版本>/` |
| 原型历史版本 | `/prototypes/<项目>/<需求>/prototypes/versions/<版本>/` |

以上均为拟定路径，尚未配置。实际部署根目录和 Web 路径需结合已有服务器核实。

文档与原型分别维护不可变版本，版本号可使用提交 SHA 加包内容摘要。固定入口引导到对应版本 URL，避免页面与资源跨版本混用。固定入口不使用长缓存，历史版本资源可设置较长缓存。

每个包记录需求标识、类型、提交 SHA、指纹、流水线、发布时间、当前及上一版本、访问链接。

## 11. 文档与原型的关联

| 位置 | 链接规则 |
| --- | --- |
| 需求导航 | 指向最新文档与最新原型 |
| 已发布文档中的原型引用 | 指向明确的原型版本和页面锚点 |

- 单独更新原型，不改变历史文档引用。
- 文档需要关联新版原型时，发布新文档版本。
- 同时发布两者，先准备并验证目标原型版本，再发布引用它的文档。
- 原型尚未生成时，文档标注未提供，不创建无效链接。
- 依赖的原型版本准备失败，引用它的新文档不发布。
- 原型引用变化参与文档包指纹计算。

## 12. 回滚、归档与清理

文档和原型独立回滚，不修改 Git 历史，不影响其他需求。回滚前校验目标版本及依赖，并记录操作结果。

回滚后，下次正常发布仍以仓库内容为准；如需持续保持回滚状态，应显式停用对应包的自动发布。

历史清理必须保留：

- 当前使用的版本。
- 明确留档的评审版本。
- 被保留文档引用的原型版本。

保留期限与数量实施时确认，未确认前不自动删除。归档和下线不释放需求标识。

## 13. 旧产物兼容与代码调整范围

| 对象 | 后续调整内容 |
| --- | --- |
| 创建需求入口 | 标识输入、自动生成和唯一性检查，在 `requirements/` 下创建需求 |
| 技能与模板 | 取消低保真，调整生成顺序，将默认根目录改为 `requirements/` |
| 规格及治理校验 | 移除低保真前置条件，适配新路径 |
| 导航和链接 | 适配目录及版本关联 |
| 发布脚本 | 独立打包、指纹、部署和回滚 |
| CI 配置 | 触发、标识检查、串行部署和报告 |
| 使用说明 | 创建、分享、重试、回滚和下线 |

已有产物不自动删除或批量搬迁：

- 已有 `outputs/product-requirements/<旧目录>/` 通过登记映射兼容，新需求不再写入旧根目录。
- 为旧需求分配标识时检查冲突。
- 已有低保真文件可留档，新流程不再生成或要求补齐。
- 明确迁移至 `requirements/<需求标识>/` 时，同时更新登记、内部引用和路径校验，验证文档与原型链接；保持需求标识和对外访问地址不变。
- 不借迁移修改既有业务需求内容。

## 14. 实施顺序与待核实条件

| 阶段 | 交付 |
| --- | --- |
| 环境与约定核实 | GitLab、Runner、发布分支、路径、网络及服务器情况 |
| 创建和生成流程调整 | 唯一标识、新目录、取消低保真及兼容逻辑 |
| 本地发布能力 | 独立打包、依赖检查、指纹与版本关联 |
| 部署能力 | 上传、切换、状态记录、失败恢复和回滚 |
| CI 接入 | 发布任务、凭据配置和结果报告 |
| 服务器配置与联调 | Nginx 路径、发布权限和端到端验证 |

实施前核实 GitLab 地址与版本、业务仓库、可用 Runner、目标服务器系统、现有 Web 服务、端口及路径占用、磁盘空间与网络连通性。确认历史保留策略及实际发布清单。

使用专用发布账号和 SSH 密钥，核验服务器主机密钥。凭据不得写入仓库、文档、日志或生成产物。网页访问权限与 GitLab 权限独立；第一版访问者必须能够连通该私网。

后续代码实施须先检查已有能力再修改。相关变更验证完成后按既有授权本地提交；推送和服务器变更按届时用户授权执行。

## 15. 验收标准

| 场景 | 预期 |
| --- | --- |
| 手动输入合法标识 | 创建对应需求目录并登记 |
| 标识留空 | 自动生成合法且不重复的标识 |
| 标识重复或非法 | 阻止创建，不覆盖已有需求 |
| 多分支出现重复标识 | 合入检查或发布检查发现并阻断 |
| 新建需求 | 无低保真生成及评审要求 |
| 新需求目录 | 创建于 `requirements/<需求标识>/`，不额外生成 `outputs/` 层 |
| 需求资料归属 | 原始需求、确认记录、文档和原型均归属同一需求目录，持久资料纳入 Git |
| CI 打包 | 临时文件不回写需求目录、不提交 Git |
| 旧目录兼容或迁移 | 登记可定位资料，内部链接有效，需求标识与对外地址不变 |
| 只改文档或原型 | 仅对应包产生新版本 |
| 内容不变或仅改过程材料 | 不重复部署 |
| 新增需求 B | 不改动需求 A 的发布版本 |
| 修改共享资源 | 仅实际受影响的包更新 |
| 包内删除文件 | 新版本不残留被删除文件 |
| 部分发布失败后重试 | 保留可访问旧版，补发未完成包 |
| 连续推送 | 旧任务不能覆盖新版本 |
| 独立回滚 | 仅改变目标包入口 |
| 查看历史文档 | 仍能访问对应原型版本 |
| 清理历史版本 | 不删除仍被保留文档引用的原型 |
| 删除需求目录 | 报告待下线，不自动删除线上内容 |
| 内网实机访问 | 页面、资源、跳转和关键交互正常 |

实施进度分别记录“实现完成”“自动验证通过”“最终验收完成”。本方案文档保存不代表代码实现或部署完成。
