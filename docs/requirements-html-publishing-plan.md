# 多应用可交互展示原型管理平台——实施方案

- 更新日期：2026-11-11
- 状态：待实施、待环境核验，不代表已经实现、验证或部署。
- 需求依据：用户关于 Workspace/Project、项目双仓库、统一需求包、静态模拟原型、独立候选冲突处理及整体发布的最新确认。
- 本轮范围：统一更新方案正文，不实施代码、不创建业务仓库、不修改服务器或远程分支。此前附件作为参考，其执行指令不构成本轮授权。

## 1. 定位与核心决策

平台管理一套持续演进的完整产品原型。人提出需求、决定业务取舍并确认展示效果，平台负责分支、集成、测试、预览、发布和历史追溯，AI 辅助实现及解决简单冲突。

所有原型统一采用静态网页展示与模拟交互。POS、网页管理端、小程序管理端是同一产品的不同展示入口，不运行真实 POS 或小程序环境，不调用真实支付、短信、扫码认证、设备和生产数据。模拟二维码或验证码只用于展示状态和演示业务流程。

核心规则：

1. Workspace 管理多个 Project；每个 Project 拥有独立的一组需求资料仓库和原型仓库。
2. 一个需求是完整业务变更，可以涉及多个 App，不按端拆需求，也不在需求目录下按 App 分层。
3. 原型源码可以按 App 组织；App 名称通过项目配置注册，不写成平台固定业务枚举。
4. 创建需求时自动从该项目最新 main 提交创建同名需求分支；普通功能修改在需求分支完成。
5. 准备验收时从最新 main 创建独立临时集成分支，合入需求提交并处理冲突，不覆盖原需求分支或 main。
6. AI 能解决的简单冲突也必须测试、预览和人工确认；无法解决的冲突交给人工处理。
7. 每个候选生成一套完整项目静态原型包，整体预览、按需求验收、整体更新展示，不独立发布某个 App。
8. 人工批准绑定固定候选提交与完整产物，发布使用该产物，不重新构建替代；本轮交付完成须具备原型确认、成功发布及需求变更合入 main 三项事实，不能发布后长期待合并却标记交付完成。
9. 验收快照不可变，合并和发布事实另行追加关联。查看旧版本时按固定提交或 Tag 检出对应原型，不依赖持续变化的分支 HEAD，也不回滚当前产品。
10. 新项目直接使用本结构；旧系统迁移不是本方案的实施前置条件。
11. 需求可主动选择已进入 main 的版本同步开发基准；同步保留本需求修改，冲突处理完成并验证后更新基准，不自动合入其他未进入 main 的需求分支。

取消低保真阶段，保留已有满足要求的页面、交互与设计规范。原型验收、原型发布与真实业务软件上线分别记录，不能用一个 Done 混为一谈。

流程以方便修改、快速预览、保留确认依据为主。同一需求内的小修正继续在原需求分支迭代，开发预览可持续更新；需要更新已确认展示时生成新的固定候选，按修正涉及的内容确认后热更新。热更新指切换到新的完整静态包，不覆盖历史文件。不要求先回滚，也不引入复杂的撤销批准流程。

## 2. Workspace、Project 与数据权威来源

### 2.1 组织与 Git 边界

```text
Workspace：业务团队
├─ Project：零售产品
│  ├─ retail-requirements
│  └─ retail-prototype（POS、管理后台、小程序模拟页面）
└─ Project：供应链产品
   ├─ supply-requirements
   └─ supply-prototype
```

平台层级为 Workspace → Project → Requirement。Workspace 是组织和访问管理边界，不对应一个包含所有项目的 Git 仓库。Project 是 Git 集成、完整原型构建、发布与回滚的边界；不同项目各自的主线变化不使对方候选过期。

每个仓库已绑定项目，仓库内无需重复 workspace/project 两层目录。经常由同一需求共同修改的 POS、后台和移动页面应属于同一 Project。跨 Project 需求协调不纳入首版自动集成流程。

| 对象 | 标识与职责 |
| --- | --- |
| Workspace | workspace_id，组织项目与访问范围 |
| Project | 平台唯一 project_id，归属 workspace_id，绑定两个仓库 |
| Requirement | project_id + requirement_id，完整业务变化，与 Plane 原始工作项 ID 映射 |
| App | project_id + app_id，原型中的展示入口，不是独立需求或发布单元 |
| PrototypeChange | change_id，需求的一轮交付，关联该轮候选、验收和发布；首版一个需求一个活动 Change |
| IntegrationAttempt | attempt_id，一次冻结来源的集成尝试 |
| PrototypeBuild | build_id，一套完整项目静态原型产物 |
| AcceptanceSnapshot | snapshot_id，固定人工确认的候选与产物依据 |
| IntegrationRecord | 实际合并结果，关联 snapshot_id 与 MR |
| ReleaseRecord | 实际整体发布结果，关联 snapshot_id、build_id 及实际合并记录 |
| DeliveryRecord | 某需求 Change 的交付结果，同时关联确认、合入 main 与成功发布依据 |

Project ID 全局唯一，因此内部可以用 project_id 直接定位，外部按 Workspace 路由时必须核对归属。需求 ID 在项目内唯一、归档后不释放；App ID 在项目内唯一。分支、MR 和展示版本号均不能代替长期业务标识。

### 2.2 组件与权威来源

| 内容 | 权威来源 |
| --- | --- |
| 需求流程、责任人、业务状态 | Plane 工作项，平台保存映射和必要缓存 |
| PRD 内容与修订 | 需求资料仓库的仓库标识、文件路径、精确 Commit |
| 原型代码与需求包 | 原型仓库的精确 Commit |
| 人工验收依据 | 需求资料仓库中受控、不可覆盖的验收记录 |
| 集成与发布执行事实 | 平台追加的运行记录，关联 GitLab MR、提交及实际发布结果 |
| 可恢复原型内容 | 固定 build_id 的不可变完整归档 |

VitePress 发布文档，GitLab 管理两仓库与 MR/CI，Nginx 服务静态原型，Codex 执行受限修改。平台服务协调事件、候选、验收及归档；可采用模块化单体，语言和数据库根据现有环境确定，不预先拆微服务。OpenHands 等编排不是首版依赖。

人工批准由真实身份和受控流程确认，不能靠 PRD 中 approved 字段、普通分支 YAML 或 AI 自述代替。数据库索引可缓存验收结果，但不能成为第二套可随意修改的审批真相。

工具仓库 Requirement-AI-Toolkit 维护技能、模板、校验和发布能力，不作为某项目的需求或原型业务仓库。

## 3. 新项目仓库与配置

### 3.1 目录结构

```text
{project}-requirements/
├─ requirements/
│  └─ req001/
│     ├─ prd.md
│     ├─ decisions.md                 # 按需记录业务确认
│     └─ acceptance-records/          # 受控验收记录
├─ standards/
├─ .vitepress/
└─ README.md

{project}-prototype/
├─ prototype.yaml
├─ apps/
│  ├─ pos/src/
│  ├─ admin/src/
│  └─ mobile/src/
├─ packages/
│  ├─ prototype-sdk/                  # 场景、导航、语义定位与消息协议
│  ├─ prototype-player/               # 配套演示控制器、评审旁栏与 walkthrough
│  └─ mock-runtime/                   # 页面会话内的模拟状态与响应
├─ requirements/
│  └─ req001/
│     ├─ manifest.yaml
│     ├─ annotations.yaml
│     ├─ scenarios.yaml
│     └─ walkthrough.yaml
├─ schemas/
├─ tests/
├─ scripts/
├─ AGENTS.md
└─ .gitlab-ci.yml
```

需求资料仓库保存业务文字与确认；原型仓库需求包保存本需求统一的标注、场景及演示步骤，不重复 PRD 全文。需求包没有 App 子目录，也不另设跨端流程目录，跨应用演示直接写入 walkthrough。

apps 下名称只是示例，可为任意符合命名规则的 App。按应用划分源码便于维护，不代表分别创建需求、审批、发布或回滚。共享代码仅按实际需要提取，不强制所有页面共用 UI。

SDK 及配套演示代码统一在 packages/ 下随原型版本提交。构建时将 SDK、演示控制器、评审旁栏和模拟运行代码一起打入完整包，历史回放运行该包自己的完整代码；平台负责授权与入口解析，不加载最新版演示代码替代历史代码。

### 3.2 prototype.yaml

```yaml
schema_version: 1
workspace_id: team-a
project_id: retail
repository:
  default_branch: main
applications:
  - id: pos
    name: POS 展示原型
    root: apps/pos
    build_command: pnpm --filter pos build
    output: apps/pos/dist
    entry: /login
  - id: admin
    name: 管理后台展示原型
    root: apps/admin
    build_command: pnpm --filter admin build
    output: apps/admin/dist
    entry: /settings
```

配置只声明应用名称、源码位置、静态构建命令、输出目录和入口。每个应用输出均为静态 HTML/CSS/JavaScript 和所需资源，由项目打包器统一收集；不设置预览类型选择或能力矩阵。

workspace_id、project_id 必须与平台注册关系一致。app_id 使用安全的小写字母、数字和连字符，不允许路径分隔符或路径穿越；root/output 解析后必须位于本项目隔离工作区。构建脚本运行在受限 Runner，不允许项目配置扩大部署权限或取得生产凭据。

每次候选冻结其配置版本。本次需求包按候选配置验证应用引用；过去已验收的需求包投影到当前原型时，缺失目标作为失效诊断，不以修改历史包来消除错误。历史回放按快照内配置运行，不向当前配置查询旧构建的入口。未来新需求删除展示入口时，当前视图明确提示已删除，历史快照仍保持原始内容；这是新平台历史保护，不是旧系统兼容层。

## 4. 需求 ID、创建与分支

需求 ID 沿用已有规则：手动输入英文字母和数字且两者均有，去首尾空白后转小写；空值生成 req＋日期＋随机字母数字，例如 req20261110a7f3c9。手动重复提示重输，自动重复重新生成；项目内唯一且不释放。Plane UUID 或展示编号独立映射，不直接假定其适合作为分支名。

创建流程：

1. 获取 Workspace、Project、需求 ID，验证项目归属与两个仓库配置。
2. 幂等登记需求及 PRD 路径，读取原型仓库 main 精确 SHA 和当时最新发布记录。
3. 从该 SHA 创建名称严格等于需求 ID 的原型分支。
4. 保存 origin_commit、分支和当时已发布版本；需求包骨架可在首次开发时提交。
5. 创建失败记录阶段并允许重试；已有同名分支先核对归属，不接管或覆盖未知工作。

需求资料仓库使用其常规编辑/MR 流程，不要求机械创建第二个同名分支。创建原型分支本身不构建、不部署；允许大量空闲分支，不主动批量同步。

首次及后续每轮开发前检查基准，展示当前基准与 main 可同步版本，由需求选择同步目标，不因 main 更新自动修改需求分支。无独立提交时可快进，有骨架或其他独立提交时保留未交付修改并受控同步，不强制重置。origin_commit 固定为需求首次创建的起点，永不覆盖；working_base_commit 仅在实际吸收对应主线后更新。main、需求预览和当前产品发布版本分别记录；main 合并成功但发布尚未完成时，不将主线版本误报为当前产品版本。

req001 等需求分支在开发、验收和发布后均保留，后续修改继续使用原分支，只有明确废弃需求时才删除。每轮交付创建独立 Change；原型确认、成功发布且本需求已确认变更合入 main 后，本轮 Change 才交付完成。完成前的修订和候选重试仍关联该 Change，不因一次重试新开交付轮次；交付后继续修改同一需求则开启下一 Change，无需新建需求。验收、发布和合并分别记录，但合并是交付完成条件，不再采用“发布即完成、合并以后再说”的口径。

上一轮交付时完成已确认变更的主线集成，下一轮选择对应主线版本受控同步回原需求分支，以吸收候选中的冲突修复。交付前重试时，本需求尚未合入的已确认修复须明确带入本需求的新候选并验证，不能因只使用原需求分支而丢失；未交付修改不得被覆盖。这不授权纳入其他尚未合并的需求。

一个需求可以只改资料而不改原型。按统一创建规则可以已有空分支；确认原型不适用后结束该 PrototypeChange，记录不适用原因，保留需求分支，不制造候选或原型验收。

### 4.1 同步到指定主线版本

需求提供“同步基准到指定版本”操作。例如 B 从 main 的 1.0.1 开发，main 已推进到 1.0.5，用户可在 B 中选择“将基准同步到 1.0.5”。平台将该版本对应的主线提交合入 B 原需求分支，保留 B 的功能修改，不创建新的需求，也不把 B 合入 main。

可选版本必须能唯一定位本项目原型仓库中已进入 main 的精确提交，可使用已有 Tag 或平台版本记录，不要求每个需求都建 Tag。显示版本号、提交 SHA 和当前基准；仅已展示但尚未进入 main 的原型版本不能冒充主线版本。请求开始时冻结目标 SHA，即使 main 随后推进到 1.0.6，本次仍同步 1.0.5。

执行规则：

1. 记录同步操作 ID、所属需求及当前 Change、同步前分支 HEAD、旧 working_base_commit、目标版本与精确 SHA、发起人及时间。同步本身不是新交付轮次。
2. 在隔离工作区基于冻结的 B 分支 HEAD 执行 Git merge；无独立修改时可快进，不通过 reset 或强制推送丢弃 B 的修改。原工作区未提交内容不被移动或覆盖，需先保存为提交才能纳入本次同步。
3. 有冲突时保存现场和报告，AI 可处理实现层面的简单冲突；无法确定或涉及业务取舍时交给人工。业务规则、范围或验收条件变化按第 6.2 节先更新依据并确认，再基于新依据重新尝试，不以同步为名改变原要求。
4. 冲突解决后提交合并结果，运行与变化相关的检查；存在冲突修复时还须预览并人工确认处理结果。成功后仅在 B 分支 HEAD 仍等于操作开始值时更新原分支，并更新 working_base_commit 为实际吸收的目标 SHA；若期间有人提交，保留结果并基于新 HEAD 重试，不覆盖其修改。同步验证不代替后续原型验收。
5. 失败、未解决冲突或取消时保留操作记录，不把基准标为同步成功；原需求分支和 main 不受该失败尝试影响。同一操作重试幂等；目标已被分支包含时报告已同步，不制造重复合并。选择更旧且已包含的版本不会降级或删除后续修改。

同步成功后可刷新开发预览，既有候选、验收快照与已发布包保持不变；需要确认新结果时创建新的候选尝试。开发基准同步与最终集成分开：B 可以在选定的 1.0.5 上继续开发；准备合入 main 时仍从当时最新 main 创建候选，并适用第 9 节的基线检查，不能凭旧版本同步成功绕过合并门禁。

## 5. 统一需求包、场景与标注

### 5.1 Manifest

```yaml
schema_version: 1
requirement_id: req001
title: 启用短信验证码登录
prd:
  repository: retail-requirements
  path: requirements/req001/prd.md
  commit: <完整PRD提交SHA>
affected_apps: [admin, pos]
acceptance_criteria: [AC-001, AC-002]
annotations: annotations.yaml
scenarios: scenarios.yaml
walkthrough: walkthrough.yaml
review_scope:
  - id: admin-sms-settings
    app: admin
    route: /settings
    role: focus
    regions: [login.sms.settings]
    allowed_controls: [login.sms.enabled]
    acceptance_criteria: [AC-001]
  - id: pos-sms-login
    app: pos
    route: /login
    role: focus
    regions: [login.sms.panel]
    allowed_controls: [login.sms.phone, login.sms.code, login.sms.send, login.sms.submit]
    acceptance_criteria: [AC-002]
  - id: pos-home
    app: pos
    route: /home
    role: context
    whole_page: true
    allowed_controls: [home.back]
```

affected_apps 说明业务影响和检查范围，不拆出 App 级审批或必需/可选开关。所有 PRD 验收条件在一个需求级结果中逐项记录确认依据；小修正可按第 9 节沿用未受影响项的原确认。同一验收条件可以覆盖多个应用。影响清单不能代替共享逻辑回归分析，也不能用于跳过已确认业务要求。

四类 YAML 都版本化并校验格式及跨文件引用，PRD 引用指向精确内容而非最新网页。无原型变化时不要求补齐无意义演示文件。

review_scope 声明本需求的评审页面范围：focus 为重点评审页面，context 为完成演示必需的辅助页面，不代表该页发生了业务修改。范围 ID 在需求包内唯一；页面由 app 与 route 联合定位。regions 使用稳定的区域语义 ID，整页关注则明确声明 whole_page: true，两者互斥且必须选择一种。关注区域与允许操作分开：allowed_controls 声明本页或当前步骤允许交互的语义 ID，标注层高亮并开孔，其余应用操作由遮罩屏蔽。whole_page 只表示整页关注，不自动放开全页操作。

同一路由中承载其他功能的 Tab、面板或弹窗，可用 states 区分功能视图及其可操作目标；不逐一登记输入值、加载中、校验错误等流程内部状态。输入框、返回、关闭及必要确认操作也应纳入允许操作集合，不能只开放重点业务按钮而卡住流程。弹窗或演示步骤变化时按本需求配置更新开孔。可通过 scenario 声明初始场景，但同一演示切换页面不重新初始化；场景切换与页面导航分别处理。

需要原型展示的 PRD 验收点必须至少关联一个 focus 页面或区域；无页面表现的验收点明确说明验证方式，不制造无意义页面。评审范围只限定浏览与关注内容，不缩减完整构建、整体发布或必要回归范围。范围随需求包版本化并冻结在候选及历史包内。

### 5.2 标注

```yaml
schema_version: 1
annotations:
  - id: anno001
    type: element
    scope_id: admin-sms-settings
    target:
      app: admin
      route: /settings
      element_id: login.sms.enabled
    title: 启用短信登录
    acceptance_criteria: [AC-001]
  - id: anno002
    type: element
    scope_id: pos-sms-login
    target:
      app: pos
      route: /login
      element_id: login.sms.entry
    title: 短信验证码登录入口
    acceptance_criteria: [AC-002]
```

标注属于需求，target.app 只说明展示位置，不形成端目录。使用稳定 data-prototype-id 或 SDK 语义 ID；同一 App 渲染范围不允许歧义重复，不要求不同 App 的同名元素全局互斥。

每条标注通过 scope_id 关联评审范围，目标页面、状态和元素必须位于该范围；旁栏 note 即使没有元素目标也必须关联范围，仅在对应范围内展示。查看 A 只加载 requirements/A/ 下的标注及评审配置，查看 B 只加载 requirements/B/ 下的内容；不叠加、不跨需求引用标注。修改 A 不得编辑 B 的标注，候选差异检查应核对这一边界；正常同步主线已有版本不等于授权重写其他需求标注。范围缺失、区域不存在或标注越界时明确诊断，不能静默扩大范围或随机匹配。

支持 element、note、walkthrough、change 等版本化类型。旁栏 note 无元素目标时不强制 element_id。标注不能作为业务规则唯一来源，验收点必须存在于绑定 PRD。

定位检查仅针对本次查看或验收的需求，报告需求、App、元素、路由、场景和固定构建。缺失、歧义、不可见均明确显示；坐标只能是标明可靠性的辅助，不能把错误定位当成功。A 的标注定位结果不作为 B 验收或发布的门禁，也不得通过修改 A 标注使 B 校验通过。若主动用 A 标注查看变化后的当前产品，定位失效只在 A 视图提示，不随机开孔到其他元素；历史查看使用固定版本的 A 页面与 A 标注。必要业务回归仍检查功能，不等于跨需求加载或修改标注。

模拟状态默认仅在当前页面会话内有效，刷新后重置；同一演示页面内的跨应用操作共享该会话状态，不跨标签页或构建共享可变状态。新窗口即使继承固定版本与评审范围，也初始化独立模拟状态，不恢复上个页面的持久化业务数据。

## 6. 功能开发与独立集成候选

### 6.1 正常需求开发

新增独立业务需求通过同名需求分支修改；同一需求内的小修正继续使用原分支。开发预览可以随分支变化，但不能自动更新已确认展示或作为最终验收依据。发现问题后直接修订、重新预览，按需要确认新的固定候选后热更新，不强制先回滚。复用已有原型能力，不为每个需求复制整套源码。

AI 普通功能开发在需求分支；集成冲突修复在本次隔离候选工作区。两种情况均不得直接修改 main，也不能由 Agent 自行签发人工验收。

### 6.2 集成与冲突处理

1. 准备验收时冻结批准 PRD、需求源 HEAD 和最新目标 main SHA。
2. 从目标 SHA 创建新的 integration/{requirement_id}/{attempt_id} 临时候选分支和隔离工作区。
3. 合入冻结的需求提交。无冲突也必须测试，不能把 Git 成功当作业务正确。
4. 简单代码冲突由 AI 尝试解决，保留原冲突、处理差异、依据和影响报告；限制尝试次数、时间及修改范围。
5. 无法解决、规则互斥或业务含义不明确时进入 awaiting_manual_resolution，保存现场并交给人工。
6. 仅改变实现方式且满足原要求的处理，可由人工或 AI 在当前候选隔离工作区继续；保留实际处理者和差异。人工决定涉及业务规则、需求范围或验收条件变化时，先更新对应需求依据并由有权确认业务的人员确认；当前尝试停止进入验收，保留处理记录，基于新依据创建新的集成尝试。
7. 处理完成后提交候选、执行测试、构建完整原型并生成固定预览，人工判断整体效果。

候选处理中允许新增修复提交；一旦进入可验收预览，candidate_commit 与产物冻结。再有修改则创建新尝试或候选修订，保留旧记录，重新测试和确认。不得反复覆盖同一已供审查的预览。

冲突处理不得覆盖原需求分支。AI 不能通过删除测试、禁用功能或忽略错误消除冲突；旧能力仍有效时保留，当前需求明确替换旧行为时按新要求执行。无法确定由人决定。

冲突处理不得隐式改变已确认的业务要求。业务确认记录关联确认人、时间和精确需求依据；不能仅把取舍写进冲突报告，就继续按旧 PRD 验收。需求分支与需求合并候选保持隔离：B 同步的主线版本可以包含 A 已经合入 main 的结果，但不能为了整体展示而自动把 A 尚未合并的分支或候选纳入 B。指定版本同步不是跨需求合并。

候选驳回后保留报告和已确认决策，再修订需求分支、生成新候选；可参考旧修复，不机械复制整个候选。每个 Change 可关联多个尝试及候选 MR，记录实际采用的候选；候选重试不是新一轮交付，不将需求与 MR 永久绑定为一对一。

### 6.3 登录需求示例

```text
main@v0.0.1：账号密码登录
├─ reqqr001：二维码登录需求分支
└─ reqsms001：短信登录需求分支

二维码需求 → 候选 → 测试与人工确认 → 合并与发布 v0.0.2 → 本轮交付完成
短信需求 → 从 v0.0.2 的 main 创建新候选 → 合入短信需求
         → AI/人工解决冲突 → 测试与预览 → 人工确认
         → 合并与发布 v0.0.3 → 本轮交付完成
```

版本号仅用于说明；不要求每次合并都创建正式 Tag。短信候选应同时保留仍有效的账号密码和二维码登录，并新增短信流程。最后合并的是已确认候选，包括其中的冲突修复，不是再合并一次原短信分支。

上例假定二维码候选已合入 main 后再创建短信候选；短信需求也可以先主动同步到包含二维码能力的主线版本，再继续开发。若二维码尚未合入，不自动将其候选纳入短信需求。两个需求分支发布后均保留。

## 7. 整体构建、预览与演示验证

每次需要构建的候选统一构建项目全部已注册应用，收集为一个完整静态包。应用构建命令只是内部步骤，不产生独立发布或验收单元。首版不实现逐 App 产物复用、独立晋级或单端发布。

```text
项目构建包/
├─ index.html                     # 项目/需求展示入口
├─ apps/
│  ├─ pos/
│  └─ admin/
├─ requirements/                  # 运行标注、场景和演示所需资产
├─ runtime/                       # 本版本 SDK、演示控制器、旁栏与模拟代码
└─ build-manifest.json            # 固定应用入口、源码和资源摘要
```

build_id 指向完整包，记录 candidate_commit、项目配置、依赖与工具链信息、需求包摘要、SDK 版本及内容摘要。可对包内文件计算摘要用于校验，但不维护独立 App 发布版本。相同完整包摘要可以共用归档，构建执行来源单独记录。

所有资源和模拟数据包含在包内，不引用会被覆盖的共享运行资源。部署前验证固定子路径、深层刷新、懒加载、图片和脚本引用。预览与正式入口解析到同一固定产物地址，不能为了修改 base path 重新打包后沿用旧批准。

展示与演示验证范围：

- 配置、本次需求包、PRD 验收点和应用引用有效；不以其他需求的标注定位结果阻断本需求。
- 全部注册应用构建成功，入口及必要资源可访问。
- 本需求场景和关键既有场景能够初始化并完成模拟交互。
- 同一需求的跨应用演示、语义标注、步骤顺序和必要视觉状态正确。
- 本需求评审页面、区域和允许操作引用有效；遮罩开孔、必要输入及辅助操作正常，其余操作不可点击，越界导航提示是否退出评审，明确退出后可完整浏览。
- 无真实支付、短信认证、设备及生产接口调用；模拟动作有确定结果。
- 按变化运行必要类型检查、单元测试和浏览器回归，不把原型验证扩展成真实业务后端或终端认证测试。

正式候选仍需人工判断业务表达和展示效果，自动测试通过不能替代验收。只有文档或验收记录变化时，不重建未变原型。开发分支无原型或演示变化时不制造新预览，失败补发不能被路径过滤漏掉。

## 8. 需求入口与固定演示版本

统一入口：`/workspaces/{workspace_id}/projects/{project_id}/requirements/{requirement_id}`。

| 视图 | 内容 |
| --- | --- |
| 开发预览 | 需求分支最新有效构建，可变，明确不是最终验收依据 |
| 待验收 | 指定 attempt_id 的固定完整项目包 |
| 历史版本／验收 | 按固定 SHA 或 Tag 检出所选版本查看原型；验收原始效果可使用对应 snapshot_id 的归档包，仅加载本需求标注 |
| 当前产品 | 当前成功发布的完整项目包，按需展示该需求的标注 |
| 需求差异 | 使用 Git/MR 提供的候选与目标 main 差异；业务变化由本需求说明表达 |

应用切换菜单来自所选包内的项目配置，需求入口可突出受影响应用，不按端拆成多个需求页面。同步主线和合入 main 使用正常 Git merge，有冲突就处理；不增加自动业务差异归因功能。A 未合入 main 时 B 不包含也不负责保留 A；A 已合入时 B 按选择的主线版本吸收其结果。完整构建只是构建本候选已有的整套代码，不表示自动组合其他未合并需求。

### 8.1 需求评审模式与范围约束

需求开发预览、待验收和历史验收入口默认进入需求评审模式，只加载本需求的标注与操作范围。旁栏按 review_scope 列出重点页面及验收点，辅助页面标记为“流程辅助”。首次进入初始化场景；之后选择条目仅导航、定位和高亮，保留当前模拟数据。需要主动切换场景时明确提示重置，不因切换条目静默恢复预设数据。

评审采用“遮罩限定操作＋越界提示退出”。标注层高亮本次允许操作的按钮、输入框等，并为其开孔；其余应用操作屏蔽点击，同时阻止键盘触发被屏蔽控件。弹窗或步骤变化时同步更新允许操作，返回、关闭、输入等必需操作不能遗漏。导航检查作为意外跳转的兜底，不仅依赖遮罩：

| 操作 | 评审模式下的行为 |
| --- | --- |
| 进入已声明的重点页面或功能视图 | 正常进入，仅显示本需求标注，并更新允许操作的高亮与开孔 |
| 进入已声明的辅助页面或功能视图 | 正常进入，标为流程辅助，开放其必要操作 |
| 点击未开放的应用控件 | 遮罩屏蔽，不触发原操作 |
| 已开放操作意外触发范围外跳转 | 暂停跳转，提示“即将离开本次需求评审范围，是否退出评审并继续浏览？” |
| 自动重定向、模拟登录后跳转、跨应用切换 | 使用相同检查，不能绕过范围 |
| 浏览器前进、后退或直接访问评审会话内的地址 | 越界时使用同一提示；选择留下则恢复最近允许位置，无有效位置时返回需求评审入口 |
| 普通链接、新窗口或外部地址 | 同样检查；范围内新窗口继承固定版本与评审上下文，越界须明确退出后继续，不自动放行 |
| 用户选择“退出评审并继续” | 解除遮罩及评审限制并进入目标；原型内导航仍用同一固定包，显示“完整产品浏览”状态 |

提示提供“留在评审”和“退出评审并继续”。留下时保留当前页面与模拟数据；继续意味着明确退出评审，不是扩大本需求范围。完整浏览中提供返回需求评审入口，返回时恢复本需求遮罩与操作范围，仍保留同一会话数据。普通输入、加载与校验结果随流程正常变化，不逐一登记为功能视图；必需弹窗及其关闭、确认控件随当前步骤配置开放。

例如短信登录评审允许“后台短信设置 → POS 短信登录 → 登录成功首页（辅助）”，登录成功跳转正常执行且保留后台设置结果；库存管理按钮被遮罩屏蔽。若自动跳转到库存管理，则提示是否退出评审后继续。必需流程被遮罩阻止时报告本需求配置缺口，修订后重新验证，不自动扩大范围，也不修改其他需求标注。

所有应用接入同一版本化 SDK 导航约定，覆盖应用路由、普通链接、新窗口、跨应用消息及语义状态切换；不能仅靠外层 iframe 或鼠标点击拦截宣称范围约束成立。评审约束用于聚焦需求，不替代 Workspace/Project 访问权限。

### 8.2 固定版本与 SDK

一次打开候选或快照后，整个演示会话固定 build_id/snapshot_id。当前产品入口也只在打开时解析 current，随后切换应用沿用同一个完整包；显式刷新至新版本时提示版本变化。不在每次应用切换时重新读取 current。

当前包无法定位旧标注时显示失效或目标已删除；历史包保持原样。历史定位按其包内配置，不能因当前应用列表改变而丢失旧入口。历史验收入口始终指向所选修订当时确认的候选包，默认显示最近一次已交付修订的原始确认包；尚未交付的已确认候选另列，实际交付版本另外展示，不用后续交付包替换原验收入口。未验收需求显示待验收，纯文档需求显示原型不适用。

原型使用版本化浏览器 SDK，支持场景初始化、应用切换、语义定位和演示步骤。外层与 iframe 之间采用含消息类型、requestId、schemaVersion 的协议，检查来源窗口、Origin、目标 Origin、格式和权限，配置 CSP/frame-ancestors。应用的模拟业务状态由受控场景接口处理。

历史回放使用原包内配套的 SDK 与完整演示代码，不加载最新版替代，也不要求新版平台演示控制器解释旧协议。包内代码或资源缺失时报告恢复失败，不用静态页面可见冒充完整交互恢复；这用于新平台自身历史回放，不引入旧项目结构兼容。

## 9. 人工验收与受控合并

验收单位是一个需求修订及其完整候选原型，按 PRD 验收条件逐项记录结果。条件可涉及多个应用，但没有独立的 App 批准状态或以可选端绕过需求的开关。

小修正只需人工确认本次修改及受影响内容，未受影响的验收项沿用原确认依据，不要求重走全部人工验收。新确认仍绑定新候选和完整产物，逐项记录本次复核结果或所沿用的原确认记录及适用说明；必要自动检查照常执行。业务规则变化仍先确认对应需求依据，再确认受影响流程，不把沿用旧依据当成跳过已变化内容。

确认与展示流程：

1. 固定候选完成测试，完整产物已可靠保存且可访问。
2. 用户查看需求、固定候选、场景、标注、演示步骤及适用的冲突报告。
3. 真实登录验收者确认具体候选；平台保存不可变验收快照及受控批准记录。
4. 记录写入需求资料仓库成功后，才允许更新已确认展示或进入合并门禁；缓存或内存批准不够。
5. 交付时通过 MR 将本需求已确认变更合入 main，并完成确认产物的发布；只有确认、合并、发布都完成才结束本轮 Change。交付前可持续更新需求预览，但不能以已有预览代替合并完成。已确认候选是本需求分支与 main 的集成结果，包含冲突修复，不引入其他未合并需求。

人工批准绑定固定 candidate_commit 与完整产物。每次最终检查与合并按 Project 串行，全部常规 main 更新经过同一受控入口。合并前核对候选、需求依据、测试、需求包和快照一致，且没有待人工处理事项；main 若已偏离该候选的 target_main_sha，则不得直接合入，须重新集成、测试并验收，原批准保留为历史。实际合并必须拒绝过期结果，不能先读取 main 后无条件提交合并。

采用 fast-forward 合并，禁用 squash 和验收后 rebase，使 main 指向已验收 candidate_commit。平台合并身份与开发 Agent 分离；main 受保护，可信检查和合并权限不能由普通候选改写。

修订产生新的候选、需求依据、标注、场景或演示内容时，旧批准不授权新结果；新尝试重测并按变化确认受影响内容，保留旧记录。原需求分支后续提交不改写已冻结候选，也不自动纳入其合并或发布；合并使用已确认候选，不使用分支最新 HEAD 替代。验收记录自身新增元数据不算 PRD 内容变化：批准引用精确 PRD 提交，并核对被批准文件及其明确依赖的内容，而不是要求资料仓库整个 HEAD 永远不变。

候选成功合入后，发布依据为批准记录、实际合并记录与产物摘要，不再使用合并前的 main 一致性条件。交付前已展示的候选若因 main 变化重新集成，保留原确认与展示事实，新结果按受影响内容重新确认；最终交付关联实际合入的结果与成功发布依据，不用旧批准冒充新结果。修订、热更新和主线集成分别记录，不引入撤销批准流程。

GitLab 版本、许可证、保护分支及合并 API 能力在环境核验时验证。不假定普通 MR approval 等于强制门禁。只能人工受控合并时明确标为流程门禁及自动化未完成，不宣称自动闭环通过。

批准记录保存真实确认者、时间、逐验收条件结果及快照 ID；小修正的记录区分本次复核项与沿用原确认依据的项，并保存原记录引用。快照在合并前即可成立，不包含尚未发生的合并和发布事实。快照内容不可变，后续修订生成新记录并关联同一需求及所属 Change，不覆盖过去记录，不新增复杂的撤销批准状态。

交付确认可直接引用本包原有验收记录；后续包代为交付时，可在该包验收中同时确认前序需求的有效能力，不另设一套审批流程。

origin_commit 为创建需求时主线，永不覆盖；working_base_commit 只表示需求分支实际吸收的基线；merged_commit 表示实际合入事实；正式 baseline_tag 可按发布节奏创建，不要求一需求一 Tag。需求首次进入正式 Tag 的关联一旦登记不随以后发布改写。

运行状态分开表达：候选 awaiting_acceptance/approved/rejected/stale；冲突 awaiting_manual_resolution；合并 pending/merged/failed；发布尝试 pending/published/failed；重试任务可标记 superseded（已被后续发布替代）；交付 pending/delivered。stale 表示该候选不能按原基线直接合入，不抹掉其历史批准或已发布事实。失败注明阶段，不因发布失败抹掉验收和合并事实，也不把失败尝试改写为成功。

## 11. 整体发布、失败恢复与回滚

需求未合并时可以更新本需求的开发预览或固定确认预览，彼此隔离。交付时将已确认变更合入 main，项目当前产品发布使用对应已确认完整包：取得项目发布锁，检查批准记录、实际合并记录、固定候选和产物摘要，校验归档和入口，验证页面及资源，原子切换项目 current 指针，检查访问并登记发布结果。已经打开的演示继续使用原固定包；不通过发布 B 自动组合尚未合并的 A。

项目包缺文件、任何应用构建或验证失败，都不发布半套原型。应用间没有独立晋级路径。后台用项目展示操作顺序约束执行：旧任务不得覆盖最新展示决定，包括热更新和主动恢复旧展示；重试幂等，不重复制造验收快照或发布事实。操作序号等细节不要求用户管理。

发布失败时，保留旧 current、已确认快照及已有合并记录，记录失败原因和待重试状态；尚无成功交付依据时不标记已交付，也不自动撤销源码。切换后检查失败时，在该操作仍是最新展示决定的前提下恢复上一指针，不能覆盖后续操作。需求文档发布和原型发布是跨仓操作，分别报告结果、补发缺口，不能伪装原子跨仓事务。

允许后续需求继续交付：A 已合入 main 但原型发布失败后，B 可以同步包含 A 的主线版本，继续验收、合并和发布，其完整包保留 A 的有效变更。B 发布成功且有权确认业务的人员确认该包保留 A 的有效能力后，追加“A 随 B 对应版本交付”的交付记录，关联 A 的 Change、原始快照、实际发布记录和完整包。不能仅凭提交祖先关系推定能力保留，也不能据此自动把尚未进入 main 的 A 合入 B。

需求预览彼此隔离，B 不负责组合或保留 A 尚未合入 main 的展示内容。当前产品持续通过各需求交付合并推进；A 先合入 main 后，B 正常同步主线并处理冲突即可。不新增跨需求展示组合或“代其他需求合并”的流程。

A 的原始验收入口仍指向 A 候选包，原发布尝试保留失败及原因；A 的待重试任务标记为已被后续发布替代，不得再覆盖当前版本。A 展示已交付，同时可查看原始验收、失败尝试与实际交付版本。B 失败或未确认保留 A 时，不据此完成 A 的交付。

查看旧版本通过检出对应的历史原型版本实现，不改变 main 或当前产品入口，不因此引入交付撤销或回滚状态。主动恢复旧展示仍是独立的可选操作，不是查看历史的前置步骤。发现问题可直接在原需求分支修正、重新预览，只确认修改及受影响内容后更新展示；未受影响项沿用原确认依据，最终按本轮 Change 的确认、合并与发布条件完成交付。

文档按需求增量发布，只修改文档或登记验收不会重发未变原型。临时构建目录不提交源码仓库。目录或登记删除仅报告待处理，不自动清空线上内容。

## 12. 历史归档与清理

历史查看先选择需求及其固定版本，在独立工作区检出该版本的完整提交 SHA 或固定 Tag，按当时的依赖、配置、SDK 和演示代码运行原型。需求分支会继续迭代，不能只检出同名分支的最新 HEAD 冒充历史；历史查看不切换当前开发工作区、不修改 main，也不更新 current。仅加载该版本中所选需求自己的标注和评审范围。

已保存的同版本完整包可以直接用于查看原始验收效果；需要从历史提交重新构建运行时，记录其来源并标明为历史源码重现，不冒充当时验收的原始 build_id，也不替换原归档及确认记录。依赖缺失或构建失败时明确报告，不用最新代码替代。源码历史与原始产物共同留存，不因支持检出就删除已发布或已验收包。

保存三类对象：受控验收和执行索引、不可变完整项目包、在线访问副本。历史引用关联完整 build_id，不按 App 分拆归档。相同完整内容摘要可去重，首版不做文件块级去重或复杂冷热存储平台，不自动清理已发布及已验收包的归档和在线副本。

历史包包含所有应用静态资源、项目配置、需求标注、场景、演示步骤、SDK、配套演示代码和模拟数据。只保存 Git 源码或截图不算满足可交互历史回放。

在线缓存缺失时，授权查询、按 build_id 加恢复锁、校验摘要、安全解压、原子进入只读缓存，返回同一固定入口。页面展示恢复进度、失败和重试；损坏时不能回退到最新版冒充历史，也不从当前源码静默重建。

当前版本、验收引用版本、明确留存的评审版本及被文档引用的包必须可恢复。定期校验、备份元数据与完整产物并演练恢复。首版不设置已发布及已验收原型包的自动过期清理；恢复流程用于副本意外丢失、损坏等情况，被引用的最后一份归档不得由普通清理任务删除。

需求分支在开发、验收、发布后长期保留，仅在明确废弃需求且确认无待交付内容后删除；纯文档需求按第 4 节结束 Change，但保留分支。临时候选分支仅在交付、必要主线集成和历史入口验证完成，且无待处理内容后清理，不删除尚待合并的候选。归档需求不释放 ID，删除分支不删除历史记录。

## 13. 平台接口、权限与执行边界

采用模块化服务，职责包括 Workspace/Project 登记、应用配置解析、需求同步、候选集成、冲突执行、完整包构建预览、需求验收、整体发布和历史恢复，不拆成多个独立服务作为首版前置条件。

建议接口：

```text
GET  /api/workspaces/{workspaceId}/projects
GET  /api/projects/{projectId}/apps
POST /api/projects/{projectId}/requirements/sync
GET  /api/projects/{projectId}/requirements/{requirementId}
POST /api/projects/{projectId}/requirements/{requirementId}/integrations
POST /api/projects/{projectId}/requirements/{requirementId}/base-syncs
GET  /api/base-syncs/{syncId}
GET  /api/integrations/{attemptId}
POST /api/integrations/{attemptId}/acceptance
POST /api/integrations/{attemptId}/merge
GET  /api/projects/{projectId}/requirements/{requirementId}/views
GET  /api/snapshots/{snapshotId}
POST /api/snapshots/{snapshotId}/restore
```

所有操作校验 Workspace/Project 权限，不能仅凭知道全局 ID 就访问；POST 幂等或支持幂等键。验收身份来自真实会话，服务签发受控记录，不接受伪造审核人。Agent 不持有 main 直接推送或验收签发权限。

建议实体为 workspaces、projects、requirements、prototype_changes、integration_attempts、prototype_builds、acceptance_records、snapshots、integration_records、release_records、delivery_records、archives、audit_events、webhook_events。App 是配置中的展示项，不引入单端批准或单端发布表。

Plane 事件验证来源、去重和重试，必要时轮询与对账；不能假定实例支持尚未验证的 Webhook 或字段。只同步指针与状态摘要，PRD 和验收内容分别保留自己的权威来源。

普通开发工作区与冲突工作区均隔离，构建和预览只用模拟数据，部署凭据不暴露给候选脚本。GitLab 仓库权限不等于静态页面权限，预览和历史访问需独立校验。

## 14. 分阶段实施

| 阶段 | 工作与完成定义 |
| --- | --- |
| P0 环境核验 | 确定 Workspace/Project 映射、新项目双仓库、GitLab/Plane 能力、Runner、身份、Nginx 和归档；产出现状与差异，不执行旧项目迁移 |
| P1 新结构与自动分支 | 建立至少两个静态展示应用、配置及统一需求包；幂等创建同名分支，空分支不构建；支持指定主线版本同步及冲突人工处理，保留未交付修改；完整项目包可预览 |
| P2 场景与演示 | 本需求标注隔离、遮罩限定操作、越界提示退出；跨应用 walkthrough 保留会话数据，仅规定的初始化动作重置 |
| P3 候选与验收发布 | 跑通固定候选、确认、fast-forward 合并和完整包发布，三项完成才结束 Change；支持小修正沿用未受影响项确认依据，再接入 AI 冲突修复及人工接管 |
| P4 历史与恢复 | 按固定提交或 Tag 独立检出历史原型，保留原始验收包、完善恢复与备份；历史查看不改变主线或当前展示 |
| 后续可选 | 业务差异可视化、影响分析、自动编排等，按实际需求另行确定 |

P3 首个正式验收闭环就必须可靠保存完整产物和验收记录，不能等到 P4 才保留历史；P4 完善访问与运维。新建未预设 App 只需配置和该应用源码，平台核心不添加业务端名分支。

已有目标服务器信息为私网 10.94.164.176，仅作待核验实例配置，不是平台常量。先检查实际 GitLab 版本、许可证、分支与 MR API、保护规则、Runner、Plane 接口、域名、页面权限、空间及备份，不能把曾可用当作本次已验证。

本方案直接面向新项目和新结构，不建设旧目录、旧地址或旧数据兼容层。确有旧资料导入需求时单独立项，由用户明确输入、目标和验收依据，AI 可以辅助迁移；不将迁移作为当前阶段前置工作，也不自动删除旧资料。

## 15. 验收剧本与完成标准

### 15.1 并行登录需求及冲突

1. 初始项目 v0.0.1 只支持账号密码登录；创建 reqqr001 和 reqsms001，均记录同一 origin_commit。
2. 二维码需求在自己的分支修改，生成候选，经测试和人工确认后合入 main 并整体发布 v0.0.2，本轮交付完成。
3. 短信需求可先同步包含二维码能力的指定主线版本，再从最新 main 创建临时集成分支。另验证二维码尚未合入时，短信需求不包含也不负责保留它，不自动组合两者的需求预览。
4. 分别验证无冲突、AI 能处理的简单冲突、必须人工解决的冲突；都不修改原需求分支或 main。
5. 人工处理后仍重新测试、预览并确认，将已确认变更合入 main 并发布同一完整包 v0.0.3，完成本轮交付。若合并前 main 偏离集成基线，重新集成并确认受影响内容，原确认与预览保留。
6. v0.0.3 保留仍有效的三种登录方式；二维码需求历史仍显示其原验收版本。

### 15.2 一个需求跨多个展示入口

1. 一个需求同时涉及后台设置与 POS 登录，统一写入该需求四类 YAML，不创建端目录。
2. 在同一候选中从后台演示切换到 POS，展示状态与标注对应正确。
3. 演示期间发布新的 current，原会话仍使用原完整包，显式打开新版才切换。
4. 按同一 PRD 的验收条件整体确认，不新增逐 App 审批或独立发布步骤。
5. 需求入口只加载本需求标注，列出重点及辅助页面；首次进入初始化场景，之后点击旁栏仅导航定位。后台修改后切换 POS 仍保留结果，不重置为场景默认值。
6. 高亮并开放当前步骤的按钮、输入框和必要返回、关闭操作；其他控件由遮罩屏蔽且不能通过键盘触发。弹窗和步骤变化后开孔同步更新，错误提示等流程内部状态正常展示。
7. 自动跳转、跨应用导航、前进后退、新窗口和直接访问发生越界时提示是否退出评审；选择留下保留页面与模拟数据，选择继续明确退出后进入目标。
8. 退出后解除遮罩，原型内仍浏览同一固定包并标明完整产品浏览；返回评审恢复本需求遮罩及操作范围。首次进入、主动切换场景、重置和刷新才初始化模拟数据。
9. 本需求缺少必需操作或辅助页面时报告配置缺口，不自动扩大范围；查看 A 不加载 B 标注，修改 A 不改 B 标注，B 的验收不受 A 标注定位结果阻断。历史查看使用固定版本对应需求的标注及范围。

### 15.3 失败与历史保护

| 条件 | 预期结果 |
| --- | --- |
| 重复需求事件或部分创建失败 | 幂等重试，不覆盖未知分支，不丢失原始来源 |
| 大量闲置需求 | 不为每个分支构建或运行独立服务 |
| 已确认内容被修订 | 新候选重新验证并按变化确认，旧批准与旧包保留，不覆盖历史 |
| 需求源分支继续开发 | 已冻结候选保持不变，新提交不自动混入其发布或合并 |
| 合并前 main 偏离候选集成基线 | 不直接合入，重新集成并验收，原批准保留为历史 |
| 候选正常合并后 main 已变化 | 发布核对批准、实际合并记录及产物摘要，不再套用合并前 main 一致条件 |
| 两个候选并发合并 | 项目门禁拒绝过期候选，无检查后无条件合并窗口 |
| AI 无法解决冲突 | 保存现场，进入人工处理；人工解决后仍需测试与预览确认 |
| 冲突取舍改变业务规则、范围或验收条件 | 更新需求依据并经有权人员确认，旧尝试停止进入验收，新建尝试；仅实现方式变化可在原尝试继续 |
| 验收记录保存失败 | 不允许更新已确认展示或合并，不用缓存批准冒充持久记录 |
| 一个应用构建失败 | 完整包不发布，不产生部分新版 |
| 合并成功但发布失败 | 旧 current 可用，验收和合并事实保留，发布幂等重试 |
| 已确认且预览可用，但未合入 main | 不标记本轮交付完成；确认、合并及成功发布都完成才结束 Change |
| A 已合入 main 但发布失败，B 成功且确认保留 A | A 原验收包及失败记录不变，追加随 B 交付关联，保留 A 自己的合并依据，A 显示已交付，A 重试任务被替代 |
| B 失败或未确认保留 A | 不因此将 A 标记为已交付 |
| 旧发布任务晚完成，或回滚后旧任务重试 | 不覆盖最新展示决定，包括主动恢复旧包 |
| 确认后发现小问题 | 原需求分支修订，只确认修改和受影响项，其他项引用原确认依据；交付前沿用当前 Change，交付后修改开启下一 Change |
| 本轮交付完成后再次开发 | 原需求分支保留，受控同步 main，不覆盖未交付修改；新交付轮次用新 Change，候选重试沿用当前 Change |
| B 从 1.0.1 同步到指定主线 1.0.5 | 保留 B 修改并吸收目标主线内容，origin_commit 不变，成功后 working_base_commit 指向 1.0.5 的精确 SHA |
| 同步期间 main 推进到 1.0.6 | 本次仍同步冻结的 1.0.5，不静默切换目标 |
| 同步发生冲突 | 隔离处理，必要时人工接管，验证及冲突处理确认完成后才更新原分支与基准 |
| 同步期间 B 收到新提交，或同步失败、取消 | 不覆盖新提交；失败或取消不更新原分支与基准，保留记录 |
| 目标版本不存在、歧义或尚未进入 main | 明确报告原因，不猜测版本、不自动合入其他需求 |
| 重复同步或选择已包含的旧版本 | 幂等或报告已包含，不回退分支、不制造重复合并 |
| 保存验收记录或只改文档 | 不重建未变完整原型 |
| 明确废弃后删除需求分支，或在线副本意外丢失 | 历史完整包、标注和演示仍可恢复；首版不自动清理已发布及已验收包 |
| 新版本 SDK 或平台上线 | 历史使用包内 SDK 与配套演示代码，不加载最新版替代 |
| 刷新页面或打开另一个演示页面 | 刷新重置模拟状态，不同页面会话互不污染，同页面跨应用联动仍有效 |
| 查看 A 或 B 的标注 | 各自只加载本需求标注；A 的定位问题不阻断 B 验收或发布，修改 A 不得改 B 标注 |
| 查看旧版本 | 独立检出固定 SHA 或 Tag，使用该版本原型、SDK 及所选需求标注；不修改 main、开发工作区或 current |
| 历史源码重新构建 | 标明来源与重现性质，不冒充原始验收包，不覆盖原确认记录 |
| 缺失引用、重复目标、非法 SDK 消息 | 明确拒绝或诊断，不伪造展示成功 |
| 归档损坏 | 报告错误，不以最新版替代，不删除最后可恢复副本 |
| 纯文档需求 | 原型标记不适用，结束 Change 并保留需求分支，不制造原型验收 |
| Workspace 下不同 Project 更新 | 各自仓库、候选和发布独立，不因对方 main 更新而失效 |

完成要求：满足对应业务验收点，展示与演示测试可复现，来源 SHA 和完整产物摘要可追溯，文档、配置与测试保持一致。分别报告实现完成、自动验证通过、最终业务验收完成；执行记录另区分验收、合并和发布。

本轮文档提交只代表方案整理完成，不代表上述系统能力已开发或部署。
