# 需求探索机制场景走查

本记录是对技能入口、探索指引、产物说明和 PRD/BDD 模板的人工流程推演。以下内容为测试输入及按规则推演的处理结果，不是真实用户需求或确认记录；未启动独立模型会话，也未生成业务原型，不代表浏览器端到端验收。

## 1. 模糊需求与有条件比较

输入：“增加批量审批。”没有痛点、规模和审批限制信息。

推演结果：已知事实仅为用户提出此功能；“重复点击耗时”只能作为假设。先询问主要耗时发生在逐项判断还是重复操作，以及哪些事项必须逐项审阅。不立即生成批量操作页面，不虚构效率提升数字。

若测试补充回答为“判断很快，主要是重复提交；每项仍须人工查看，不允许自动批准”，可比较“逐项查看后集中提交”与“保留逐项提交并改善连续处理操作”。前者减少提交次数但需明确部分失败和选择范围，后者改动小但仍需逐项提交；在重复提交为主要痛点的条件下推荐前者，部分失败规则保持待决定。自动审批与补充约束冲突，不作为候选；推荐仍需随业务模型确认。

判定：通过。能探索真实目标，按事实筛选候选并比较实质取舍；不把例子固化为新增范围。

## 2. 已确认的简单修改

输入：已有业务模型和低模确认，用户要求把原型按钮“确定”改为“提交审批”，流程与权限不变。

推演结果：读取确认记录，核对按钮所在入口和文案缺口，按原路径更新并进行对应验证；不要求重新选择业务方案，不为文案修改生成三套方向，不因跳过探索而跳过原型检查。

判定：通过。成熟度分流与旧确认复用兼容，仍遵循实际变更所需验收。

## 3. 未回答关键规则

输入：批量提交的失败语义未定，不知道应全部回滚还是允许部分成功；用户暂未回答。

推演结果：可以比较两种语义的成本和用户影响，整理已确认的入口、角色及状态草案；失败反馈场景放入“待确认草案”。不选择其中一种作为规则，不生成依赖它的正式原型或正式 BDD，亦不宣称业务模型已确认。

判定：通过。等待范围限定于依赖决策的动作，独立分析仍可继续；正式交付生成时机未提前。

## 4. 参考与设计系统门槛

输入 A：业务目标已知，但没有截图参考，也没有用户明确的无参考继续决定。

推演结果：继续目标与方案讨论，记录参考待决；不生成低模。用户后续明确无参考继续，才按原流程记录低置信度需求基线。

输入 B：PRD/BDD 已批准，设计系统仍为 candidate。

推演结果：可继续准备视觉候选和设计系统评审，不生成业务高模；探索许可不改变高模 approved 门槛。

判定：通过。分别保留参考决策、实际读图、低模确认与设计系统批准边界；相关脚本正反例仍适用。

## 5. 否决建议与旧任务恢复

输入：用户否决自动审批，仅保留人工审批；旧任务的业务模型和低模已确认，现在继续正式需求交付。

推演结果：读取原文和最新确认，把自动审批记为暂不纳入；正式规则、原型和 `.feature` 不出现自动审批场景。继续已获准阶段，不要求补历史方案比较。如新证据只涉及失败后的重试，仅分析其影响，不重新打开其他已确认权限。

判定：通过。范围来源不变，否决项不混入承诺，新增未知按依赖局部处理。

## 结论与验证边界

五组人工流程走查均可在当前规则中得到一致处理。正式 HTML 名称、编号、生成时机与治理接口保持不变。自动检查覆盖格式、引用和既有治理行为；本记录不证明模型在所有真实对话中的稳定表现，后续应以实际使用反馈评估探索质量。
