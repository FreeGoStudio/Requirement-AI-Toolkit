# 产品需求与 Storybook 原型

以用户原始需求与明确确认作为依据。需求文档使用 Markdown，可交互原型使用 Storybook；不再生成低保真阶段、HTML 需求正文或独立流程 HTML 副本。既有视觉、组件与有效交互继续复用。

## 工作目录与恢复

先核对用户指定仓库的 `git worktree list --porcelain`、当前分支、AGENTS.md 和状态。用户指定 Storybook 分支时，使用实际检出的 storybook worktree，不能误用同仓库 HTML 分支或已安装的旧版技能。平台服务源码和技能源码分属不同项目；从平台 README/IMPORT 确认服务主维护目录，不在技能仓库复制平台实现。

读取 [输出与项目契约](references/output-artifacts.md) 和 [生成、校验与交付](references/storybook-workflow.md)。业务项目复用其需求分支与独立工作目录，说明精确路径。技能目录不作为业务源码仓库；技术验收示例可按用户授权保存在技能仓库 examples 中，明确是隔离演示而非已交付业务项目。

## 需求与确认

沿原始需求完成问题澄清、业务对象、状态和验收条件。未知规则标为待确认，已有确认不重开。保存有实际内容的原始需求、业务模型、PRD、BDD 和流程图；不预建空文件。PRD 和 BDD 通过后制作原型。用户明确要求技术验收样例时，可按已授权技术场景选择最小示例行为，但须记录假设，不能冒充真实产品业务验收。

参考和视觉规范优先复用已有资产。无参考的业务产品先明确方向；技术验收样例沿用平台现有样式，不新增品牌设计审批。页面中的用户输入安全渲染，不调用真实支付、短信或生产系统。

## 生成与验证

读取平台当前模板及四类 YAML 的实际 Schema，按 workflow 生成 Storybook 应用壳、页面和 Stories。统一 npm 锁文件、稳定 app + route 与 Story ID；跨应用状态由播放器持有，Story 局部状态不承担跨应用数据真相。不要求重写为 React。

先校验需求引用、入口映射、场景及标注，再构建所有注册应用和播放器，最后浏览器验证真实 Storybook 画布、Manager、直接入口、跨 Story/App、刷新、固定子路径和历史包。未通过的检查标明失败，不用组件可见或模拟测试代替业务流程验收。

## 发布与验收

使用平台需求预览与候选流程，详见 workflow；可使用同仓库 `prototype-publish` 技能核验完整包发布契约。开发预览不要求合并或最终批准；正式交付必须绑定固定候选、真实人工确认及明确交付授权，合并后发布同包。

Plane 是需求与人工评审入口；不得由 Agent 代签或写入伪装人工通过的评论。正常自动化完成后回写固定链接与实际执行状态。发布受阻时报告具体条件，保留上次成功入口，不改用旧 Html 发布模式绕过。

区分源码生成、自动验证、真实交互验证、人工验收和发布。历史独立 HTML 的转换须另外授权，现存旧 references/scripts 仅服务历史探索，不作为新 Storybook 项目的默认输出或发布规则。
