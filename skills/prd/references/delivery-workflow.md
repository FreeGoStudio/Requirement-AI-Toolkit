# 文档与 HTML 原型交付

产品经理负责确认需求和发布时机，分支、图片路径、提交和 MR 交给技能处理。用户用任务编号和文档表达意图即可，不要求其手动执行 Git 命令。此流程用于已要求的 GitLab/VitePress 交付，不把每次本地生成都变成发布任务。

## 入口与项目配置

先读取原始要求、最新确认、项目 AGENTS.md 和维护入口，检查已有仓库、未提交改动、远端、发布分支、站点构建及发布规则。复用现有 Runner、导航和发布机制，不因使用本技能重新搭建基础设施。

从项目现有配置读取文档仓库路径、GitLab 项目、目标分支、站点地址及构建/预览命令；必要时再向用户询问缺失值。不要将某台电脑路径、任务编号、账号或站点地址写死在通用技能中。凭据使用已有认证或受限本地配置，不写入交付文件和提交。

记录本次任务编号、源文件、目标目录和已有确认。区分“准备预览”“提交评审”“发布上线”的授权；明确要求提交 GitLab 评审时可执行对应推送和创建 MR，不额外逐条询问技术步骤。只要求准备或预览时先完成本地工作；不得据此推送或合并。创建 MR 不授权发送邮件、聊天通知或修改 Plane。

## 准备分支与产物

1. 获取远端最新状态，从实际目标分支创建任务分支，例如 `docs/TODO-13`；遵循项目命名规则，无约定时使用 `codex/docs-TODO-13`。已有属于同一任务的分支/MR 时检查后复用；不要复用其他任务的工作分支，也不强制重置、暂存或覆盖用户已有改动。必要时用独立 worktree 隔离。
2. Markdown 文档与所引用图片一起纳入仓库，修正相对路径并检查引用存在。已有 Markdown 不必为了发布先转换成 HTML，也不改写业务规则。
3. 技能生成的 HTML 文档和原型保留原格式、交互、锚点和相对资源关系。根据站点实际配置放入静态资源目录，以 VitePress 页面提供阅读入口；例如默认配置下可使用 `docs/public/requirements/<任务编号>/` 承载交付包。核对实际 base 路径，不能把完整 HTML 文档直接当作 Markdown 粘贴而破坏页面结构。
4. 只打包用户要求的文档、原型及其依赖，不整包上传含内部探索或未批准候选的输出目录。发布清单以实际文件和授权范围为准；链接依赖范围外材料时先说明，再决定移除链接或纳入材料。
5. 按现有站点规则提供导航或索引入口，避免假定任意新目录都会自动进入侧边栏。对尚未确认的材料标注草稿，不把草稿包装为已批准需求。

## 人工预览与提交评审

运行适用的链接检查和生产构建，打开本地预览供产品经理检查正文、图片、流程图和原型交互。报告自动检查结果及尚需人工确认的内容；没有实际浏览器验证时明确待验证，不代替用户确认。

本地预览和部署站点分开，预览不能覆盖已发布版本。展示本次具体差异、任务编号及拟发布入口；既有确认仅在内容未变且适用于当前版本时沿用。若用户要求先人工确认再提交，保留预览等待确认。

在相应授权范围内仅暂存本次文件，完成适用检查后按项目规则提交；允许提交评审时推送任务分支并创建或更新指向发布分支的 MR。描述包含变更内容、预览方式、验证结果和待确认项。返回 MR 链接及提交 SHA，不要求产品经理手动操作 Git。推送或 MR 受阻时保留已完成的本地结果，报告实际错误，不改权限或绕过分支保护。

## 发布与追踪

“需求内容确认”“发布授权”“业务验收通过”分别记录。确认预览不自动授权合并；发布成功不自动将 Plane 任务标记完成。只有用户明确授权当前内容上线，且满足现有合并规则时，才合并 MR；已有有效授权不重复请求。用户选择亲自合并时提供 MR 链接并停在待合并状态。

当前站点若只在发布分支更新时运行 CI，就明确说明合并前依靠本地预览，不声称已有 MR 预览站。不得为方便发布直接推送受保护主分支、降低检查或调整公网访问限制。

合并后检查流水线、实际页面和引用资源，并在有版本标记时核对提交 SHA。分别报告已提交、待合并、发布成功或发布失败，以及人工验收状态；流水线成功不能替代页面检查。失败时说明当前线上实际版本，不声称新内容已上线，也不擅自触发回滚或修改部署配置。

仅在用户要求或已授权关联 Plane 时写入文档/MR 链接，不顺带修改业务状态。后续续接读取原文、确认和当前 Git/MR 状态，不重复创建分支或 MR。
